
**「图元数」就是帧开销的主项**：【第三方实测】稳态每帧 ≈ 可见图元数 × 15~18 µs，父级隐藏时约 1/9，单次回调约 20 s 会被静默截断——数字与出处见 [rect-merge-playbook §6.1](rect-merge-playbook.md)。
> 要的是**互不重叠、精确铺满、接近原图**的纯色矩形（按 STD 控制误差）而不是形状拟合，走 [`rect-merge-playbook.md`](rect-merge-playbook.md)（工具 `scripts/rect-merge/`），两条路线的取舍见那篇 §1。（那篇的 §2.8 已经在矩形之上加了旋转矩形 / 椭圆 / 三角形 / 圆环 / 半透明和「先铺光斑」，控件数上万档、要接近原图时比本篇的随机搜索拟合更合适。）

# 图片图元拟合与 Lua 绘制

用于把图片拟合为矩形、椭圆、三角形，用千星奇域客户端 Lua 创建图片控件绘制，以及优化图元数量、画质和初始化开销。这里的图元是图片形状；节点图逻辑走 `index.md` §5。

## 2. 从图片到脚本

先确认源图、最终显示大小、透明背景需求、期望画质与现有控件预算。

1. 保留原图，另外生成裁剪/缩小的拟合输入；只在用户允许改变留白时裁剪，并保留原点与偏移关系。静态图片之外的动画逐帧拟合另行确定预算。
2. 依据当前工具选择形状、数量和 PNG 透明模式。先看目标大小下的预览，再决定是否增加细节。透明素材额外在深浅两种背景上检查边缘。
3. 保留可编辑 JSON 与预览；导出到新 Lua 路径。记录项目版本、源图、参数和实际输出图元数，便于复现随机拟合结果。
4. 核对模板索引、API、坐标与初始化，然后按 §5 检查和导入试玩。

在该项目根目录，README 给出的 Lua 导出入口是：

```sh
python server.py --cli --input input.png --export lua --output output.lua
```

参数先查该版本 `--help` 与源码，别猜 CLI 支持 `num_primitives` 等内部配置名。UI 配置用于调参时，把参数一并记录。项目支持浏览器本地 WASM 拟合；确认当前页面确实选择本地模式后使用。CLI 需要该项目的 Python 依赖与 primitive 后端；GIA 构建 README 特别注明 Python 3.13，不能套用于所有路径。优先用已有环境，缺依赖时说明具体缺项，别把下载未知二进制当成必经步骤。

## 3. 图元优化的决策

本节是优化方法，不是官方性能结论。目标是以可接受画质减少实际创建的控件；图元减少量、文件缩小量与真机帧率分别记录。

| 调整 | 适用与验证 |
|---|---|
| 减少图元预算 | 从较低数量起步，逐档增加，选择满足目标显示尺寸的最小档；例如 100/200/400 只是对照档位，不是平台限制 |
| 选择形状 | 曲面优先椭圆，块面试矩形，尖角试三角形；固定数量比较形状组合，不能照搬底层 primitive 的任意三角形假设 |
| 降低拟合输入分辨率 | 先排除最终 UI 尺寸下看不见的细节；区分搜索分辨率与导出尺寸，单改导出尺寸不能声称减少控件数 |
| 提高同预算搜索质量 | 当前实现允许时再调候选与搜索迭代次数；一次只改一个变量，并记录耗时，不能虚构未暴露的开关 |
| 精简已拟合图元 | 可试删零透明度、零面积或无贡献图元，但先确认它无事件/引用用途；每次删减后重渲染比较 |
| 背景与透明度 | 仅在目标背景相同且用户允许时跳过背景；不要把拟合 alpha 一律改成不透明 |

半透明图元的叠加有顺序依赖。不要按颜色重新排序、合并重叠半透明形状或靠包围盒认定完全遮挡。合并只在几何、颜色、透明度和层序的最终效果可证明一致时做；否则保持原顺序重拟合。

调色板去重与数据精简可以缩小 Lua，不能宣称减少实例数量。PNG 预览也不能直接当作已获得可用的游戏图片资产；用户目标是 Lua 绘制时继续走图元控件导出。

## 4. Lua 绘制与生命周期

【第三方：`lua_export.py`】导出器每个图元创建一个图片控件，矩形/椭圆/三角形使用静态图片 `100001`/`100002`/`100003`。填写 `IMAGE_PREFAB_ID` 时用客户端图片控件的**控件模板索引 ID**，不要填上述静态图片 ID。模板按项目说明设为「仅存为模板」，关闭遮罩/羽化，并挂到专用空客户端容器。

导出记录中的 `cx/cy` 是原图像素坐标，左下为原点、Y 向上；圆的宽高为直径。项目的三角形 pivot 为 `(0.5, 1/3)`，其余形状中心 pivot；保留原有层序。编辑器 JSON/CSS 的中心坐标、Y 方向与旋转约定和 Lua 记录不同，不要直接复制或重复取负。用不对称测试图检查上下、旋转与遮挡。

源码包含 `BASE_SCALE`、`FIT_TO_CANVAS`、`OFFSET_X/Y`、`SKIP_BACKGROUND`。改前核对当前生成脚本；自适应缩放不减少实例数。源导出器在 `OnStart` 创建、`OnDestroy` 清理，并在重复创建前清理。平台生命周期与模板激活行为按 `api/runtime-contract.md` §1–2 核对：只切换 active 不会重跑 `OnStart`；不要把重新启用当成首次进入。适配时保留这些效果：

- 静态图仅初始化一次；尺寸/数据变化时才更新，不在每帧全量销毁重建。
- 画布未就绪而自适应失败时，按 `lua-ui-playbook.md` 的官方示例用有界逐帧重试，成功即结束重试；不要在 `OnInit` 猜画布尺寸。
- 若大量控件初始化造成停顿，先减数量；必要时分批创建，每批数量由测量选择，并保留层序、已创建数量、完成状态与销毁取消逻辑。
- 重复打开/关闭后实例数应回到基线；清理仅限本脚本创建的控件。
- 装饰图元的点击穿透仅在当前控件 API 确认支持对应字段时设置；不把其他控件上的 `raycastTarget` 属性推给图片控件。

## 5. 检查与交付

生成/修改 Lua 时沿用 `AGENTS.md` 的脚本检查流程：先 `check-lua-ui.mjs --selftest`，再检查脚本；用 `sim-lua.mjs smoke` 搭配实际 GIL 或支持的控件树。模拟器缺少模板实例化等能力时如实列出覆盖缺口，不能用空跑代替绘制验证。只有修改存档时才追加格式检查与回读。

试玩核对：目标大小下的画质和透明边缘；模板索引与三种静态图片；上下/旋转/pivot/遮挡；自适应与不同画布尺寸；重复进入和销毁；图元峰值、初始化耗时以及适用设备上的帧耗时。离线模型不能证明真机控件容量或帧率。

## 6. 逐帧开销：先量，再改

【实测】以下数字来自一个真实项目（死亡细胞 2D 复刻，8,192 图元池、每帧约 5,600 个图元），用离线模拟器插桩统计。它们不是平台上限，只说明「该往哪里看」。

量化方法（可在任何用模拟器跑得起来的项目里复用）：给每个渲染阶段包一层计数，读 `G.drawCount` 的增量；同时统计三类「白干」——被绘制函数内部越界丢弃的调用数、细节档成本估算里逐矩形遍历的次数、图元池尾部停用的扫描次数。

| 指标（每帧均值） | 优化前 | 优化后 | 做法 |
|---|---|---|---|
| 绘制调用 | 10,576 | 5,646 | 调用前先在屏幕坐标里剔除，而不是交给绘制函数丢 |
| 其中越界被丢弃 | 5,130（49%） | 199（4%） | 同上 |
| 细节档成本估算遍历矩形 | 39,771 | 20,598 | 包围盒全可见/全不可见快路径 + 按行序二分 |
| 图元池尾部停用扫描 | 2,745 | ~0 | 记录上一帧实际点亮的高水位，只扫该区间 |
| 每帧 Lua 工时（无插桩，模拟器口径） | 269.3 / 237.5 ms | 183.5 / 162.7 ms | 合计 −32% |

可复用的精确手法：

- **包围盒快路径**：整张精灵完整落在窗口内 → 命中数恒等于矩形总数；完全在外 → 0。两个方向都可证明，不需要逐矩形扫描。
- **按行序二分**：矩形列表按行序生成时第二个字段单调不减，可把纵向可视区间换算回图像坐标后二分跳过前后必然落空的两段。下界要用 `lo - maxh`（保守），且**二分是左闭右开，1-based 数组的上界是 `#rects+1`**——写成 `#rects` 会稳定漏掉最后一个矩形，案例中正是这一处让两个后续场景出现像素差异。
- **成本结果复用**：同一帧里选档算过的每 job 成本存下来，绘制阶段直接读，别重算一遍。
- **静态数据按关卡缓存**：与镜头无关的几何（平台贴块、遮罩）只在关卡切换时算一次，逐帧只做可见性筛选。
- **只在变化时写控件**：文本、尺寸、位置逐帧重复赋值会让引擎反复重排；用缓存值比较后再写。

**浮点同序红线**：把 `world(a, b)` 内联成 `quad(a-cam, b-205-camY)` 时，必须保持原有求值顺序。`(a + b/2) - cam` 与 `(a - cam) + b/2` 在浮点下差最后一位，足以改变边缘像素。案例中曾因此让 4 张离线预览图出现差异，逐像素比对才发现。

验证方式（两步都要做）：

1. **同运行时差分**：把优化版成本估算与「优化前逐矩形实现」放进同一脚本、同一镜头下逐组比对，要求 0 不一致（案例：每个关卡各 3,000 组随机镜头，且断言其中有上千组是真实可见覆盖，避免空跑通过）。
2. **逐像素回归**：用项目既有的离线渲染器把优化前后的采集数据渲染成图，逐张比哈希（案例：24 张全部一致）。

工具：`scripts/primitive-budget.mjs frame <controls.json>` 给出重绘倍数、半透明占比与遮挡统计，先看清再决定改什么。

## 7. 图元数量的天花板（实测，别重复踩）

【实测】保像素地减少矩形数量，空间比直觉小得多：

| 做法 | 结果 |
|---|---|
| 现有贪心（宽优先，锚定首个未覆盖像素） | 1,593 个资源、523,239 个矩形 |
| tallest-first / 最大矩形 / 行游程纵向合并 / 列游程横向合并，逐像素校验后取每资源最优 | 523,148（**省 0.02%**） |
| 与真实最优对比（4,031 个真实连通分量暴力枚举） | 贪心平均超标 1.74%，96.9% 情况下就是最优，最大差 2 个矩形 |

**遮挡剔除同样不划算**：案例一帧 6,358 个图元里，23.8% 被后面的不透明图元完全遮住（并集口径，是理论上限），9.8% 可被单个后续不透明图元整个包含；但「反向扫描 + 只标记整格落在不透明矩形内的格子」这种可实现做法，在 8 / 16 / 24 / 32 px 格子下只能省 2.0% / 1.5% / 0.7% / 0.3%——为它写剔除代码是净负债。

结论：**要显著降图元数，靠的是设计选择（例如整张贴图交给图片控件承载）、细节档预算和可见性剪裁，而不是矩形合并算法。** 先用 `primitive-budget.mjs cover` 量出自己的天花板再决定。

## 8. 已核对的工具与结论（2026-10-14 实测）

【第三方】以下都实际下载运行过，注明的是实测结论而非文档说法。

| 工具 / 技术 | 实测结论 |
|---|---|
| [mikolalysenko/rectangle-decomposition](https://github.com/mikolalysenko/rectangle-decomposition)（MIT，JS，2014 停更）+ [contour-2d](https://github.com/mikolalysenko/contour-2d) | 真实精确最小分区（König 匹配）。其自带测试 960/960 通过；但**在本案例 9% 的色类上产生错误着色（22,433 像素污染）**，且有效部分只省约 2%。不要用它替换贪心。它自带的测试只比面积，抓不到污染——必须自写逐像素校验 |
| 自写贪心 + 逐像素校验器 | 案例中贪心已是最优或差 1~2 个矩形；校验器（栅格化候选，逐像素比对，分别统计污染/缺失/重叠）才是真正值得留下的产物 |
| [ImagicTheCat/ELProfiler](https://github.com/ImagicTheCat/ELProfiler)（MIT，纯 Lua） | 可用，开销实测 1.43×；但沙箱里没有 `debug` 时**加载即崩**（`attempt to index a nil value (global 'debug')`），不能进游戏 |
| 包装式（逐函数计数/计时）剖析 | 实测开销≈1.0×，不依赖 `debug`，适合在脚本内自带开关做定位 |
| [stravant/LuaMinify](https://github.com/stravant/LuaMinify)、[mathiasbynens/luamin](https://github.com/mathiasbynens/luamin) | 都能在 Lua 5.3 上正确工作，但对真实文件只省 1.7%（89% 是十六进制数据，不可压缩），**解析耗时无改善**。不值得 |
| 数据紧凑化：十六进制串改原始二进制字节串 | Lua 5.3 词法允许（实测 NUL/0xFF/非法 UTF-8 字节都能 `loadfile`），体积省 44%、解析省约 43 ms。**但 `.gil` 嵌入器是否二进制安全未验证**，采用前必须先在一个测试关卡里导入验证 |
| 预编译 Lua 字节码 | 实测加载 0.137 s → 0.012 s（**11.4×**）。**但需要客户端接受二进制 chunk（`load(..., "b")`）未验证**；不做这一步就只剩文本源码 |

`\xNN` 转义比十六进制更差（4 字符/字节），不要用。字节码与原始字节两条路互斥，且都必须先在真机验证再改交付物。
