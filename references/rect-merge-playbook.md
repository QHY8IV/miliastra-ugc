# 最大对齐矩形合并：图片 → 纯色矩形 → Lua 绘制

用于把一张图片切成**互不重叠、恰好铺满**的轴对齐纯色矩形，再由客户端 Lua 为每个矩形创建一个图片控件画出来。
工具在 [`scripts/rect-merge/`](../scripts/rect-merge/README.md)。另一条路线（形状拟合，可重叠、可半透明）见 [`primitive-ui-playbook.md`](primitive-ui-playbook.md)。

指标别只看 MAE：小而亮的细节会在平均误差里看不出来，要同时看「误差 ≥ 40 的像素数」（`bigErr`）和预期效果图的放大对比。

**边界比渐变重要时**（像素画、线稿、UI 图标、带硬边的插画）：加 `--edge-aware`，把同样的误差预算从"看不出"的平坦 / 缓变区挪到边缘（§2.9）。**2026-10-18 起它严格预算守恒**（§2.14：`--std` 决定块数，权重只决定花在哪）：2000 像素级的合成图实测边带 MAE −52%（矩形）/ −28%（形状），块数 ±0.3%；真图是否合算看「边带 MAE / 全图 MAE」，见 §2.15。旧行为（会顺手缩预算）留为 `--edge-unbalanced`。

**知道"哪里最该看清楚"时**（主体、脸、文字、UI 目标）：让 AI / 人或视觉模型给一份焦点文件，用 `--focus`（§2.10）。它和 `--edge-aware` 叠在同一条重要度图上，`--layered` / `--shapes` / `--preset best` 都能用。

**画风也是选项**（§2.16）：形状拟合的收益取决于图的**平坦区占比**。素材如果是**平涂**（大色块、≤16～32 色、干净边缘），同一套 `--preset best` 的节省从 40%～50% 抬到约 80%，并顺带把阶梯锯齿换成抗锯齿曲线。这是"出图那一侧"的旋钮，和上面几个参数旋钮正交。

**要动的是视频 / 序列帧时**（§2.17）：静态的容量公式搬过去会算错。要点是**几何按镜头分套、但只保留 2 套（双缓冲）**，加**改色门控**；**隐藏控件也要收费**（约 1.7 µs/个/帧），所以"每个镜头做一套全挂着"会掉到个位数 fps；**存档不是瓶颈，每帧绘制才是**。

## 1. 什么时候用哪条路线

| | 矩形合并（本篇） | 形状拟合（primitive-ui-playbook） |
|---|---|---|
| 画面 | 精确铺满，像素坐标对齐，无缝；误差由 STD 控制 | 矩形 / 椭圆 / 三角形叠加，逐次逼近 |

| 适合 | 要接近原图的插画、像素画、UI 底图 | 风格化、控件预算很紧 |

## 2.5 分层重长（`--layered`，本技能自研，同画质下控件更少）

铺满式划分要求矩形互不重叠，大片背景里夹着小细节时，背景得绕着细节切成好几块。控件可以叠放（后创建的盖在上面），所以：

1. 先做铺满，按面积**从小到大**处理（小块 = 细节，放最上层）。
2. 已被上层确定颜色的像素对下层是"通配"（反正被盖住）。每块从自身出发每次向四个方向之一扩一行/一列：只考虑扩完后矩形内**未定像素**标准差仍 ≤ STD 的方向，选新收进未定像素最多的那个（整行/列都是通配的方向也可选，用来跨过上层细节）。
3. 扩完后，矩形里的未定像素归它（颜色 = 这些像素的均值），矩形再缩到这些像素的外框。整块已被上层确定的块直接删除。
4. 输出倒序：底层大块先画，细节最后画在上面。

不变式：每个矩形**露出来**的像素标准差 ≤ STD——与铺满式同一条画质标准；没有完全被盖住的白建控件。`check.mjs --selftest` 逐项核对。

同 MAE 下的控件数（本机 300×300 测试插画，离线，2026-10-15）：

| 素材 | 同 MAE 下少用的控件 |
|---|---|
| 300×300 插画，MAE ≈ 0.31 / 1.24 / 3.70（STD 1 / 3 / 8） | 3.8% / 10.6% / 20.4%（STD=3：31,871 → 26,596 块） |
| 像素画（原版《死亡细胞》背景图 128² 与 256²），**无损 STD=0** | 42.3% / 36.1%（1,856 → 1,070；4,506 → 2,881） |
| 同上，STD=2 | 52.3% / 36.2% |

"同 MAE 下"的折算：用铺满式在 STD 0～16（步长 0.25）上的块数—MAE 曲线线性插值。合成测试图（大片平涂 + 圆）上 STD=8 时少约 53%。规律：平涂越多、细节越零散，收益越大；像素画、UI 图、游戏精灵收益最大。

**同一个 STD 下分层的 MAE 会略高**（矩形长得更大，更多像素贴着容差），所以比较要看同 MAE，用 `estimate.py --layered --scan-std …` 和不加 `--layered` 的结果对着挑。

```bash
python scripts/rect-merge/estimate.py --input 图.png --size 300x300 --scan-std 1,2,3,5,8 --layered
python scripts/rect-merge/compress.py --input 图.png --output out.lua --std 3 --size 300x300 --layered
node scripts/rect-merge/check.mjs render scripts/rect-merge/render.lua out.lua
```

要求与限制：
- 需要 Node ≥ 22（计算在 `scripts/rect-merge/layered.mjs`，300×300 约 0.7 秒；Python 只负责读图）。只能配 p64（坐标显式，数据顺序就是绘制顺序），输出带 `IMG.LAYERED = true`。
- **依赖"后创建的控件盖在先创建的上面"**：【第三方】形状拟合项目的 Lua 导出同样靠创建顺序保留层序；本渲染器在千星里这样叠放**未经真机确认**。`render.lua` 重建时按原顺序复用控件，层序不变。
- 有重叠就有重复绘制。外框收缩后重叠已经很少，但填充开销是否可感知要真机看。

## 2.6 写成图片素材组 .gia（静态图片，游戏里不用 Lua 建控件）

```bash
node scripts/rect-merge/to-gia.mjs out.lua -o 图.gia --unit 2 --name 图名   # 铺满或分层数据都行；--classic 写经典模式
```

- 格式依据【第三方】：[1475505/Miliastra-toolbox-primitive-shape](https://github.com/1475505/Miliastra-toolbox-primitive-shape)（MIT）的 `gia_lua.py` 读取器与 `image_template.gia`。素材组 = `resource_class` 61；子控件 GUID 列在根内容 `#503`，**前景在前**；图片组件 `#505[#502=38]→#503→#31`：`#2` 图片 ID（100001 矩形）、`#4` 颜色（ARGB 打包 uint32）；变换组件 `#505[#502=12]→#503→#13→#12→#501[平台]→#502`：501 缩放、502/503 锚点、504 位置、505 尺寸、506 轴心、508 旋转（每个控件有 4 份平台布局）；遮罩组件 `#505[#502=56]→#503→#47`：`#1` 偏移、`#2` 尺寸、`#4` 启用。顶层字段 4 = 1 是经典模式，省略是超限模式。
- 骨架 `scripts/rect-merge/gia-skeleton.json` 取自该仓库的 `image_template.gia`（根资产 + 第一个图片控件作原型），注明了来源与 MIT 许可。那个模板是第三方工具生成的：顶层字段顺序与官方存档不同（内容相同），本编码器按官方顺序写。
- 离线核对：`check.mjs --selftest` 用该项目的读取器解析我们的输出，逐条比对位置、尺寸、颜色、绘制顺序（本机已下载在 `references/community/1475505__Miliastra-toolbox-primitive-shape/`，不随技能分发；没有时这一项跳过）。
- 体积：每个图片控件约 694 字节（4 份平台布局），3 万块约 20 MB。
- **未在真机验证**：编辑器是否接受、素材组能放多少张、几万张静态图片的加载与帧率、"前景在前"是否就是叠放顺序。试验包与步骤见 `（作者本机路径，未随技能分发）`（本机）。

## 2.7 编进关卡 .gil（打开关卡即可，不用另外导入）

```bash
node scripts/rect-merge/to-gil.mjs out.lua --seed 底关卡.gil -o 图.gil --unit 2 --name 关卡名
node scripts/rect-merge/verify-gil.mjs 图.gil out.lua --unit 2      # 模拟器里运行关卡，逐像素核对
```

- 结构：底关卡里绑定了客户端脚本的那个容器 →「批1…批K」容器（每批 64 块）→「块1…块N」图片控件。**位置、尺寸写在存档里**（布局槽 (1,12)，字段【官方示例】核对过），兄弟顺序 = 绘制顺序（先画的在下面，分层数据靠它）。
- **颜色由一段很短的 Lua 开局时填**：新式客户端图片控件的颜色字段还没有证据——官方样本与本机关卡里的图片控件全是默认白色，protobuf 不写默认值。脚本每块只改 `imageColor`（另加一次 `SetImage` 设成 100001，确认默认就是纯色后可关）；**真机实测 `imageColor` 一次 1.92 µs，但完整填色路径实测 28.8 µs/块**（695 块 0.02 s，含未拆开的解码/附加调用，见 §6.1.1）——所以 3 万块的真实耗时介于 **58 ms**（纯属性写）与 **864 ms**（按完整路径线性外推）之间，取决于解码在 3 万块上的摊销，**未测**。旧估算 0.4～0.7 秒落在这个区间内，量级没错但成分不同。整体仍比现场新建控件（约 0.223 ms/个）快一个数量级以上。
- 底关卡：推荐官方 3.21「客户端脚本」示例（`mh47p30a87qo_客户端脚本.gil`，`scripts/fetch-official-samples.mjs` 可下载）。工具会清空那个容器下原有控件、把脚本换成填色脚本；底关卡本身不改（`-o` 必须是新路径）。
- 体积：每个图片控件约 810 字节（4 份布局变体），3 万块约 24 MB。
- 离线核对：`verify-gil.mjs` 用模拟器打开关卡、运行填色脚本，按控件实际位置 / 尺寸 / 颜色叠放还原画面后逐像素比对。本机 110 / 1,029 / 9,985 / 29,538 块的关卡全部一致。`check.mjs --selftest` 在设了 `RECT_MERGE_SEED`（或 `references/samples/` 里有该示例）时也会跑这一项。
- **找颜色字段**（之后就能连颜色一起写进存档、去掉 Lua）：编辑器里放一个图片控件，只把颜色改成红色存一份、改成绿色再存一份，`node scripts/gi.mjs diff A.gil B.gil`，变化的那个字段就是颜色。
- **真机（2026-10-15，编辑器 7.1.0，1920×1440）**：3～29,538 块的关卡都能加载，截图按源像素对齐后与预期效果图一致；分层数据显示正确（后创建的兄弟控件盖在上面）；外扩 0 / 0.2 / 0.5 没有可见差别、没有拼缝，所以默认外扩改为 0。觉得"分辨率低"时先看源图分辨率（`--size`），渲染本身是逐像素对的；放大显示用 `--unit`（例如 `1000 / 源边长` 让图占约 1000 单位高）。
- **`--unit` 的语义**：布局单位 / 画布像素；图的占位 = `画布边长 × unit`。固定占位换画布密度时 `unit = 占位 / 画布边长`（占位 1000：500 → 2、800 → 1.25、1000 → 1）。`verify-gil.mjs` 要传同一个 `--unit`。为什么密度比控件数更值钱、怎么挑 unit，见 §2.18。
- **老式布局「图片」控件的颜色字段已找到**（用户的红/绿对照存档 diff）：槽 (21,38) → 503 → #31 → #4，ARGB 打包；#31 #2 是图片 ID（100001 纯色）。与素材组图片同一结构。新式客户端图片控件的颜色字段仍未知。
- **全静态模式 `--static`**：以底关卡里的一个老式「图片」控件为原型（用户在编辑器的界面布局里放一个即可），图片直接挂在那个布局下，位置、尺寸、颜色全部写进存档，**没有脚本**。`verify-gil.mjs --static` 直接读存档核对（老式控件不在模拟器模型里）。

## 2.8 旋转矩形与椭圆（`--shapes`，本技能自研，2026-10-16）

**依据【真机 2026-10-16，编辑器 7.1.0】**：椭圆（静态图片 `100002`）和旋转后的控件边缘有抗锯齿；旋转角用 `SetLocalRotation(0, 0, z)`。所以斜边、圆弧不必再用一排阶梯小矩形，边缘像素可以靠覆盖率混合出来。

```bash
python scripts/rect-merge/compress.py --input 图.png --output out.lua --std 4.5 --size 500x500 --shapes   # 隐含 --layered；--shape-strength 1.5 更省控件、误差更大
node scripts/rect-merge/preview.mjs out.lua 预期效果.png                                                  # 带形状也能出预期效果图
node scripts/rect-merge/to-gil.mjs out.lua --seed 底关卡.gil -o 图.gil --unit 2 --default-layout-only    # 只走脚本版 .gil；形状的旋转 / 椭圆图由填色脚本里的 SHP 串设置
node scripts/rect-merge/verify-gil.mjs 图.gil out.lua --unit 2                                          # 模拟器里还原：位置、尺寸、颜色、图片 ID、旋转角
```

**做法（`shapes.mjs`）**：在分层矩形结果上做「率失真替换」。
- 渲染模型：画家算法，像素 = 逐层 `c += (形状色 − c) × 覆盖率`，覆盖率 = 4×4 超采样的面积占比；整图先垫一个均色底板（多 1 个控件），这样拿掉矩形后露出的是底板色，离线误差才准。
- 目标：总 L1 误差 + λ × 控件数最小。λ = 纯矩形基线「每多一个块能少多少误差」（对 STD 与 1.08×STD 各分层一次求差）× 强度。
- 每个种子矩形（面积大的在前）：从附近同色区域（容差 2×STD）的主轴得初值 → 对椭圆、旋转矩形各自爬山（位置 / 半轴 0.25 像素、角度 0.5° 量化，步长 4 → 2 → 1 逐级细化，最多 250 次评估）→ 精确评估「放上去并删掉被它取代的形状」（被取代 = 包围盒在新形状包围盒内且删掉后误差增量 < λ）→ 净收益 = 误差增量 < λ × (删掉的个数 − 1) 且至少取代 2 个才接受。共 2 遍。
- 形状的包围盒必须在图内（否则控件会画到图外）；形状总在当时最上面。输出顺序 = 幸存矩形（原顺序）再形状（创建顺序）。

**精修（默认开启，`--shape-no-refine` 关掉）**：贪心替换之后，对已有的所有形状和矩形再做几轮全局优化，每一步都按真实总误差判断：
1. 颜色重拟合：每个形状的颜色取「其它层不动时误差最小」的值（加权最小二乘，权 = 上层透射率 × 覆盖率；再用迭代重加权逼近 L1，因为指标是 MAE）。
2. 几何微调：旋转 / 椭圆形状的位置、半轴、角度逐个试 ±1 量化步。
3. 矩形边微调：每个矩形的四条边各试 ±1 像素（分层时只管露出像素的标准差，没管真实误差）。
4. 修剪：删掉某个形状 / 矩形后误差增量小于 λ 的直接删，省控件。
共 4 轮，与贪心遍数交错（3 遍，每遍之间做一轮精修）。256×256 插画 STD=6：贪心替换 7,682 控件 MAE 3.30 → 精修后 6,640 控件 MAE 2.74；同 MAE 的**未精修**纯矩形要 11,702 块（少 43%），同 MAE 的**同样精修过**的纯矩形要约 9,700 块（形状本身再少约 33%，精修本身对纯矩形也少约 15%）。精修后继续加轮数几乎没有收益。

**多线程（2026-10-16）**：搜索阶段（每个种子的区域初值 + 爬山）占全部时间的约 80%，已用 `worker_threads` 并行：主线程维护共享内存里的状态（当前渲染 `cur`、误差 `err`、每像素最上层形状 `topArr`、可见像素数 `vis`、存活与包围盒），工作线程只读快照做爬山，主线程按顺序对每个候选做精确评估并应用（所以结果和单线程基本一致，只是同批种子之间有轻微的过期）。500×500 STD 3.0 从约 8 分钟降到 1 分 52 秒（8 线程；精修和精确评估仍是单线程，所以加速比约 4×）。`--shape-threads N`（compress.py）/ `--threads N`（shapes.mjs），默认核数 − 2、最多 8。代码拆成 `shapes-core.mjs`（覆盖率、渲染、搜索器，无命令行入口，worker 可安全导入）、`shapes.mjs`（流程 + 命令行）、`shapes-worker.mjs`。

**三角形、圆环、半透明（2026-10-16；28 号校准关卡已在真机量过，建模与实测一致，仍默认关闭——要不要开看画质与控件数的取舍）**：形状种类 kind 1 椭圆（100002）、2 旋转矩形（100001）、3 三角形（100003）、4 圆环（100006）；参数里多了不透明度 `aq / 32`（颜色 alpha，`Color.FromRGBA(r,g,b,a)`）。`--shape-kinds ellipse,rotrect,triangle,ring`、`--shape-alpha`。**真机实测（28 号，从全屏截图量像素）**：三角形 = 顶点朝上、撑满包围盒的等腰三角形（z = +90 后顶点朝左）；圆环内径 / 外径 = 0.8，水平垂直都按比例缩放；颜色 alpha = 标准直接混合 `底 + (色 − 底) × α`。这些就是 `shapes-core.mjs` 里 `sdOf / insideOf / SHAPE_CONSTS` 的建模，与实测一致。256×256 插画 STD 6（精修后，同 MAE 相对未精修纯矩形少的控件）：椭圆 + 旋转矩形 43.1%；加三角形 + 圆环 47.2%；再加半透明 49.5%（只加半透明 46.6%）。数据格式 v2：`IMG.SHPV = 2`，每个形状 15 个字符 = cx cy hw hh（各 2）、`(kind−1)*512+thq`（2）、aq（1）、颜色（4）；没有 SHPV 的旧数据是 14 个字符、不透明、只有两种 kind，`blocks.mjs` 仍能读。.gil 里每个形状 3 个字符：`(图片序号*1024 + z 角量化)*64 + aq`。
半透明形状**不能直接做出渐变**——一个平涂的半透明形状内部颜色是均匀的，只有边缘有一个台阶；它的用处是盖在多种底色上做「阴影 / 高光」，一个形状代替每种底色各一块。真正的渐变要靠软边（`enableSoftEdge` / `SetSoftEdgeWidth`）：28 号实测**只有 `enableMask = true` 时才生效**，Pixel 20 + 遮罩 = 向形状内部约 10 个单位的 smoothstep 渐隐，Percentage 0.25 + 遮罩 = 钟形光斑（峰值约 0.4）；**29 号校准（真机，从全屏截图量像素）**：用 **Pixel 模式**——边缘向形状**内部**渐隐，曲线是 smoothstep，渐隐长度 L ≈ 0.82 × 宽度参数（宽度的单位是布局单位）；水平、垂直**独立相乘**：`遮罩 = smoothstep(min(到左右边的距离) / Lx) × smoothstep(min(到上下边的距离) / Ly)`；`SetSoftEdgeWidth(wx, 0)` 只在水平方向渐隐；遮罩跟着旋转走，与颜色 alpha 相乘。Percentage 模式不看宽度参数，永远是同一个钟形光斑，不能用；`horizontalSoftRange / verticalSoftRange` 没有可见作用。所以「软边矩形」是一种带两个羽化宽度（fx, fy）的形状，几个叠在一起就能搭出平滑渐变。
**软边的收益取决于图的频率（2026-10-16 复测，离线）**：原先「软边没有收益」的结论**只在高频图上成立**，不是普适结论。
- 高频细节 / 像素画（判别性测试图 B，256×256，STD 6）：椭圆 + 旋转矩形 194 控件 MAE 0.008 → 再加软边 219 控件 MAE 0.005，**多花 25 个控件只换 0.003 MAE，净亏**。原因是上面那条：软边盖在已有色块上做修正，删不掉那些色块。
- 平滑渐变 / 插画皮肤背景（真实插画 A，360×203）：STD 6 时椭圆 + 旋转矩形 206 控件 MAE 1.810 → 加软边 **191 控件 MAE 1.434**（**既省 15 个控件又降 21% MAE**）；STD 4 时 573 → 575（控件持平、MAE 0.992 → 0.745）。混合图（C）STD 4：315 → 311。
  判断标准是「这块内容还有没有低频能量可省」：MAE 已压到 0.1 以下的图没得省，插画的平滑区域有。

## 2.9 边缘优先的误差预算（`--edge-aware`，本技能自研，2026-10-17）

**问题**：矩形是轴对齐的，斜边与曲线边界只能被切成阶梯——这就是"锯齿比色差更刺眼"的原因；反过来，大片平滑渐变里块与块差 2~3 级根本看不出来。原来的判据（矩形内三通道标准差 ≤ STD）对两者一视同仁，预算花错了地方。

**做法**：给每个像素一个视觉重要度 `I`，判据换成**加权标准差**

```
I = clip(1 + boost·E − slack·(1−E), 0.2, min(4, cap))    E = |∇亮度| / max(P95(|∇亮度|), 24)
σw = sqrt( Σ I²(c−μ)² / n )  ≤  STD               μ = Σ I²c / Σ I²
```

- 边缘（`I > 1`）→ `σw` 被放大 → 同样的色差先撞上 STD → 块被切得更细，阶梯更短；
- 平坦 / 缓变（`I < 1`）→ `σw` 被压小 → 允许更大的色差 → 块长得更大；
- **精细区封顶**（`I = cap` 就不再涨）→ 噪点、发丝、星点这类"极细但对观感边际很小"的纹理不会无限吃预算；斜率按 `boost` 给，封顶位置由 `cap` 定；
- 总判据仍是 STD，所以**不是放宽画质**，只是把误差从看得见的地方挪到看不见的地方。
- `boost = slack = 0` 时**直接走不加权的老代码**（逐字节相同，`check.mjs` 里有这条断言）——两条路径的浮点运算顺序不同，不能当成"权重恒为 1"的近似。

**三条路径共用同一条判据**（2026-10-17 接通，`check.mjs` 逐条钉住）：

| 路径 | 判据落在什么上 | 恒等 |
|---|---|---|
| 纯矩形 `pack_rects` | 矩形内全部像素的 `σw ≤ STD` | `I≡1` 时逐字节相同 |
| 分层 `layered.mjs` | 每个矩形**露出来**的像素（最上层覆盖它的那些）的 `σw ≤ STD`；底层铺满也按 `σw` 切 | 同上 |
| 形状 `shapes.mjs` | 目标函数换成**加权 L1**：`Σ I·|raw−cur| + λ·形状数`，λ 由加权基线重新标定；接受 / 修剪 / 几何微调 / 颜色重拟合全部按 `I` 加权 | 同上 |

| 参数 | 默认 | 作用 |
|---|---|---|
| `--edge-aware` | 关 | 开边缘优先预算；纯矩形 / `--layered` / `--shapes` / `--preset best` 都支持 |
| `--edge-boost` | 1.6 | 明显色差处的斜率：无封顶时收紧到 1/(1+boost) ≈ 0.38 倍容差 |
| `--smooth-slack` | 0.42 | 色差不大处最多放宽到 1/(1−slack) ≈ 1.72 倍容差 |
| `--edge-cap` | 2.2 | **精细区域权重上限**：`I` 到 2.2 封顶（≈0.45 倍容差），再细也不收紧；调小更省控件、细节更糊，`≤4` |
| `--edge-ref` / `--edge-floor` | 95 / 24 | 梯度归一化的分位与绝对下限（下限防"整张图都很平"时全域被当边缘） |

**调参顺序（2026-10-18）**：先定 `--smooth-slack`（它决定平坦区放多宽，对块数影响最大），再定 `--edge-boost`（明显色差处要多紧），最后 `--edge-cap` 收口细碎纹理。在 472864868427926.jpg（细节密集）上、320×320 / STD 4.2 / 纯矩形实测：

| 旧默认 1.2 / 0.35 / cap 4 | 34,123 | 1.608 | 0.265 | 2.009 | 1.441 |
| **新默认 1.6 / 0.42 / cap 2.2** | 34,825 | **1.596** | **0.236** | 2.045 | **1.375** |

## 2.10 视觉焦点（`--focus`，本技能自研，2026-10-17）

**问题**：梯度只知道"哪里在变"，不知道"哪里重要"。一张插画里，眼睛、脸、文字标题的饱和度/对比可能很低，而一片噪点树叶的梯度却很高。**人眼（或视觉模型）指得出焦点，梯度指不出。**

**做法**：让 AI / 人先看图，产出焦点区域，再换算成同一张重要度图：

```
F(x,y) ∈ [0,1]       焦点区域（矩形 / 圆点 / 热图，可带软边），多条取逐像素最大值
I_eff = clip(I_edge + gain·F, 0.2, 4)       默认 gain = 0.8（焦点核心容差 ≈ 0.56 倍）
```

于是焦点区和"边缘"共用同一套加权判据：**哪条路径都能用**（纯矩形 / 分层 / 形状）。

**焦点文件格式**（JSON；尺寸单位可像素可归一化）：

```json
{
  "space": "norm",
  "boxes":  [ { "x": 0.32, "y": 0.18, "w": 0.36, "h": 0.42, "feather": 0.04, "weight": 1.0 } ],
  "points": [ { "x": 0.5, "y": 0.32, "radius": 0.06 } ],
  "heatmap": "saliency.png"
}
```

- `space`：`px`（默认）或 `norm`（0~1，按输出分辨率换算）；`feather` 是矩形外沿的线性衰减距离，默认 `max(4, 0.25·min(w,h))`；`points` 必须给 `radius`。
- `heatmap` 也可以**直接当文件传给 `--focus`**（一张灰度图，尺寸不同会双线性缩放）。
- 多余的键、缺字段、坐标全在图外都会**报错并指出是哪一项**——不会静默忽略（这个项目里"静默退化"已经出过好几次事）。

**怎么产出这份 JSON**：任何能看图的视觉模型都行 —— 让它返回"主体 / 人脸 / 文字 / 高光"的包围盒，转成上面的结构即可。手工标注同样有效，一个 `boxes` 通常就够。**不要让模型圈满全图**：焦点处块会更碎，全图都圈 = 全图 +8% 控件而画质没变。

**实测**（本机 600×600 插画《死生之律者》、STD=8、`--layered`；焦点 = AI 标出的「主角脸 / 窗边少女脸 / 主角躯干」，覆盖 8.9% 像素）：

| 配置 | 控件数 | 焦点区 MAE | 其余 MAE | 全图 MAE |
|---|---|---|---|---|
| 基线（分层） | 40,447 | 3.43 | 4.00 | 3.95 |
| `--focus`（gain 0.8） | 43,824（+8.3%） | **1.91（−44%）** | 4.00（不变） | 3.81 |

读法：**多花的 8.3% 控件全落在焦点区**，其余区域一个像素没变（4.00 → 4.00）。面部特写对比见 `（作者本机路径，未随技能分发）`（原图 / 基线 / 焦点三格并排），整套复现脚本在 `（作者本机路径，未随技能分发）`。

同一条链在 200×200 合成图、纯矩形路径上的对照：4,641 → 5,024（+8.3%），焦点区 MAE 1.27 → 0.58（−54%），其余 1.13（不变）。

`--focus-gain 0` 与不加权**逐字节相同**（`check.mjs` 断言），所以它也是纯超集。

**限制**：**未真机验证**；焦点只影响"预算往哪里花"，不改变总判据的口径（仍是 STD / 加权 L1）。

## 2.11 斜边补条（`snap.py`，本技能自研，2026-10-18）

**要解决的问题**：基底层永远是轴对齐矩形，斜边只能被拼成台阶；台阶的**颜色误差很小**（斜边处块本来就是 1×1），但边界是硬像素台阶，放大后看着像锯齿。旋转矩形在真机上的抗锯齿是好的（用户实测），所以沿边线铺一条细长旋转矩形，就能把这一段台阶换成一条直边。

```bash
python scripts/rect-merge/snap.py 基底.lua 输出.lua --img 图.png --render 当前渲染.png \
       --mode trim --max-strips 1200            # 只落在实测变好的位置（默认）
python scripts/rect-merge/snap.py ... --mode ridge --max-loss 12     # 骑在细线上，把白边/轮廓线拉直
python scripts/rect-merge/snap.py ... --mode pair  --max-loss 80     # 两侧成对铺成直边（牺牲 L1）
```

**怎么决定铺不铺**：不靠启发式打分，**直接实测**。`covmodel.py` 把「旋转矩形覆盖率 + 4×4 超采样」按 `shapes-core.mjs` 的 `coverageInto` 复刻了一遍，`snap-modelcheck.py` 用 5 个角度的旋转矩形跟 `preview.mjs` 逐像素对拍，**要求最大差 0**（不是"差不多"）；所以每条补条落地前都能算出它盖住的那几十个像素的 L1 变化。颜色取「盖住像素的逐通道中位数」——常数色在 L1 下的最优解。位置 / 深度 / 铺哪一侧在小网格里搜一遍。

**实测（36 号图，500×500，底子是 45 号 37,837 控件）**：

| 版本 | 补条 | 控件 | 全图 MAE | σ=0.8 模糊后 | σ=1.2 |
|---|---|---|---|---|---|
| 45 基底 | — | 37,837 | 1.3038 | 0.8180 | 0.5919 |
| `--mode trim` 900 条 | 900 | 38,737 | **1.2808（−0.023）** | **0.8002（−0.018）** | **0.5784（−0.014）** |
| `--mode ridge` 133 条 | 133 | 37,970 | 1.3024（−0.0014） | — | — |

三种模糊尺度都变好，所以不是"拿模糊换 L1"。

**结论（重要，别重复走错路）**：这张图**整个台阶误差预算只有 0.02～0.06 MAE**。原因已经查清——斜边处的块本来就是 1×1（15,427 个块里 10,936 个是 1×1；书页边缘那一带 382/561），渲染出来的边界是**每行正好推进 1 px 的 1 px 台阶**，这已经是"轴对齐矩形"能达到的最细粒度。补条能赢的只是其中"两侧都真平"的那部分；`--mode pair`（硬把边界换成直边）在 24,145 个候选点里只有 6 个能落在允许的 L1 损失内，其余一律 +200 以上——因为 1~2 px 的过渡带（缩放产生的抗锯齿斜坡、细则线）没法用常数色带复现。**所以：补条能改善一点点，但指望它把放大后的锯齿消掉是不现实的；真要更平滑，杠杆在分辨率和总控件数，不在补条。**

`--mode trim` 是纯超集：无候选落地时输出与输入的内容等价（只多写一遍文件）。**未真机验证**。

## 2.12 采样核（定案）与已否决的「边界带做柔」（2026-10-18）

**问的问题**：放大后的台阶，是不是源图 → 目标图那一步**采样**没做好造成的？

**定案（2026-10-18）**：① **采用 BOX 面积平均为默认采样核**——`compress.py` 的 `RESAMPLE` 默认已从 `lanczos` 改为 `box`，要逐字节复现 2026-10-18 之前的结果请显式加 `--resample lanczos`；② **「边界带做柔」整条线否决**，包括「σ 跟着分辨率走」那一支（§2.13 有实测）。

**先回答采样**：不是滤波器的问题，但换核**有免费收益**。

| 2500 → 500 的重建核 | 边带过渡宽度（10–90%） | 1 px 最大跳变 |
|---|---|---|
| LANCZOS（旧默认） | 4.33 px | 15.9 |
| BOX（面积平均） | 4.65 px | 15.6 |
| BICUBIC | 4.71 px | 14.7 |

三个核的**台阶幅度几乎一样**（这是 24 个边点上的实测，`_edge/probe_sampling.py`）——因为 500 网格上的信息量就那么多，换核只是换它怎么插值。**但整条管线跑完以后，BOX 全面更好**（36 号图 500×500，同样的 std 4.2 / 强度 0.9 / 焦点 / 权重）：

| 版本 | 采样 | 控件 | 对连续真值的 MAE | 边带内 | 平均台阶 | 假硬边 J |
|---|---|---|---|---|---|---|
| 45（原基线） | lanczos | 37,837 | 6.864 | 32.28 | 73.8 | 6.78 |
| **48** | **box** | **32,011（−15.4%）** | **6.544（−4.7%）** | **31.62** | **69.5** | **5.69（−16%）** |

原因：LANCZOS 在硬边两侧各留一条亮/暗过冲（振铃），拟合器把过冲当成"真结构"，于是多切块、并把那条 1 px 亮线硬画出来——J 惩罚的正是这种"真值本来是渐变的、渲染却是硬跳变"。**线稿 / 插画一律用 `--resample box`**；这个默认已经改掉（2026-10-18 定案）。

**「边界带做柔」`--edge-soft σ`（已否决，代码保留仅为复现 49/50/51/52）**：把梯度强的像素按强度混进高斯模糊版，**平坦区与小字逐字节不动**。做法在 `soften_edges()`，掩膜由梯度分位（`--edge-soft-lo/hi`，默认 10/30）给出、外扩 `--edge-soft-dilate`（默认 1，带约 3 px）。

| 版本 | σ | 控件 | 对真值 MAE | 边带内 | 平均台阶 | J |
|---|---|---|---|---|---|---|
| 48 | 0（关） | 32,011 | 6.544 | 31.62 | 69.5 | 5.69 |
| **49** | **0.7** | **28,747（−10%）** | 8.278 | 39.88 | **44.9（−35%）** | **4.87（−14%）** |
| 50 | 1.1 | 24,339（−24%） | 10.210 | 45.83 | **29.8（−57%）** | **3.83（−33%）** |

`平均台阶` = 边带内"1 个目标像素级的最大跳变"的均值，越小越不刺眼；`J` 只统计真值本身是渐变的位置。**读法：σ 越大台阶越小，但对真值的偏离（尤其边带内）成比例上升——这是拿锐度换平滑，不是变好。** 视觉上 σ=0.7 还能保住发丝/小字，σ=1.1 就明显糊了（对照图 `（作者本机路径，未随技能分发）`）。

**已知局限**：掩膜只按梯度强弱选，**不区分"长直边"和"发丝/小字"**，所以做柔会连带糊掉细节；要更挑，需要加结构张量（边缘走向一致性）判据。**全部离线，未真机验证。**

## 2.13 「轻度柔 + 更高分辨率」为什么否掉（51 / 52，2026-10-18）

σ=0.7 把 500×500 从 32,011 压到 28,747 控件，同预算自然想到把 `--size` 提到约 590——**试了，不划算**：

| 版本 | 分辨率 | 控件 | 台阶（原生） | 同显示尺寸 500 下的台阶 | J（同尺寸） |
|---|---|---|---|---|---|
| 48（不做柔） | 500 | 32,011 | 69.53 | 69.53 | 5.69 |
| 49（柔 0.7） | 500 | 28,747 | 44.85 | **44.85** | **4.87** |
| 51（柔 0.7） | 580 | 32,641 | 44.22 | 47.78 | 5.49 |
| 52（柔 0.7） | 600 | 35,887 | 44.71 | 49.06 | 5.59 |

两个原因叠在一起：① `--edge-soft` 的 σ 是**目标像素**单位，580 下的 0.7 只等于 500 下约 0.60 的物理模糊；② 拟合仍按同样的 `--std` 把边缘切得更硬。净效果是**同显示尺寸下台阶反而略差（+6% / +9%），控件却 +13.5% / +24.8%**。唯一讲得通的补法是让 σ 随分辨率缩放（580→0.81、600→0.84），但既然「边界带做柔」整条线已否决，不再推进。

**跨分辨率怎么比**：一律把各版本按面积平均缩到同一显示尺寸再量台阶，原生台阶不能横比（它是按目标像素量的颜色跳变）。

> **2026-10-20 补注**：上表的"同显示尺寸 500"是按 500 域缩的，**屏幕实际看到的是 `画布 × unit` 的显示域（本图 1000）**，两者不是一回事——按 1000 域比，625 反而比 500 好 18.8%（§2.18）。51 / 52 的否决按 1000 域复算结论可能不变，但没重跑过（产物都在，成本低）；下面"剩下的杠杆在分辨率上限和控件预算"也要改成"**控件预算**不是杠杆，**画布密度**是"。

**读这条线的教训**：台阶是"1 px 硬边界 + 放大"的必然结果，**压缩侧能拿到的改善只有采样那一份白赚的（box，§2.12）**，剩下的杠杆在分辨率上限和控件预算，不在采样核或柔化。

## 2.14 已修（2026-10-18）：`--edge-aware` 曾经会悄悄**缩**预算

**现象**（200×200 合成图，`--std 6 --shapes --shape-passes 1`，固定 2 线程；边带 = 梯度最强 4%）：

| 采样 | 配置 | 控件 | 边带 MAE | 其余 MAE | 整图 MAE |
|---|---|---|---|---|---|
| box | 不加权 | 651 | 5.070 | 2.393 | 2.496 |
| box | `--edge-aware`（旧行为） | **358** | **7.410** | 3.306 | 3.463 |
| box | `--edge-aware`（修好后） | 600 | **3.666** | 2.691 | 2.690 |
| lanczos | 不加权 | 621 | 8.708 | 2.410 | 2.673 |
| lanczos | `--edge-aware`（旧行为） | 431 | 8.028 | 3.255 | 3.454 |

旧行为下形状路径的控件数被砍掉约 45%，**边带和其余区域一起变差** —— 这不是"把预算挪到边缘"，而是把总预算砍了。lanczos 下边带看起来"变好"（8.71→8.03）只是因为它的基线边带被振铃污染，加权把边缘并粗顺手抹平了假边。

**为什么以前没暴露**：旧默认 lanczos 的边带基线太差，`see < sbe` 恰好被上面那个假象满足。换成 box 后基线修复，缺陷立刻暴露。**这是采样改进"照出来"的老问题，不是 box 引入的。**

**根因（2026-10-18 定了，与当时的推测不同）**：不是 λ 的单位错、也不是加权数学错，而是**权重同时改了"分配"和"总量"**。

- 加权铺满的判据是 `w²` 加权方差对容差 `T` 比较，于是每像素的有效容差 = `T / w`：平坦区 `w=0.58` → 容差 ×1.7，边缘 `w=2.2` → 容差 ÷2.2。
- 同一个 `--std` 下，**加权铺满的块数本来就比不加权少**（合成图 1221→1004，−18%；真图 500px 少 14%），分层再多并一遍，形状再按加权 λ 收一遍。三步叠起来就是 −45%。
- 当时把 λ 偏大当成原因，是**倒果为因**：实测加权 λ ≈ 549、不加权 λ ≈ 248，比值 2.21 正好等于 `EDGE_CAP 2.2` —— 它就是当前工作点上的真实边际价格，算得没错。错的是这个工作点的**块数**已经比用户以为的少了一截。

**修法（`layered.mjs budgetMultiplier` + `compress.py` 预算对齐）**：解一个一维方程

```
找 m，使 tile(T×m, weights).n == tile(T, null).n        （几何二分，24 次上限，实测 <0.2 s）
comppress.py 之后所有阶段（纯矩形 / 分层 / 形状）一律用 std_eff = T×m
```

语义变成：**`--std` 决定预算（多少控件），`--edge-aware` 只决定预算花在哪**。旧行为保留为 `--edge-unbalanced`（只用于复现旧结果 / 主动想缩预算时）。

**修好后的实测**（同一份 200×200 合成图、同一配方）：

| 路径 | 控件 | 边带 MAE | 其余 MAE |
|---|---|---|---|
| 纯矩形 不加权 | 1221 | 1.688 | 2.480 |
| 纯矩形 `--edge-aware` | 1225（+0.3%） | **0.808（−52%）** | 2.787（+12%） |
| 分层 不加权 | 816 | 2.311 | 2.619 |
| 分层 `--edge-aware` | 782（−4%） | **1.476（−36%）** | 2.908（+11%） |
| 形状 不加权 | 651 | 5.069 | 2.394 |
| 形状 `--edge-aware` | 600 | **3.666（−28%）** | 2.651（+11%） |

**自检钉住了什么**：
- 权重全为 1 → `m=1`，与不加权**逐字节相同**（老路径不变）；
- 默认参数块数与基线差 ≤5%，边带降 ≥10%，其余升；
- `cap / slack` 的判据从"块数多少"改成"**同一份预算下的边带 / 其余 MAE**"（块数已经由 `--std` 锁定，旧断言在新语义下必然失效）；
- `--edge-unbalanced` 仍能复现"块数 7511→5788"的旧行为，逃逸口没焊死。

**教训**：重要性权重是"往哪儿花"，不是"花多少"。两件事混在一个旋钮里，症状会伪装成"数学算错了"，而其实是**预算口径变了**。凡是要改"加权"的地方，先问一句：这次的块数该不该跟不加权一样？

**已知的不对称（先记下，别当成 bug）**：`--focus` **单独**用时仍是"加预算"语义（焦点处重要度抬高、块数会涨，不校准）；`--focus` + `--edge-aware` 同时用时，校准是按**合并后**的重要度算的，于是焦点也变成"在固定预算里换位置"。要不要把 focus 也默认对齐，等有真实用例再定。


## 2.15 修好之后在真图上还值不值（36 图 500px，2026-10-18）

**为什么修好了也不管用（这一条比结论重要）**：这张图的边带 MAE 是 **31.5**，而全图 MAE 只有 6.5 —— 边带误差比全图高 5 倍，说明边带里装的**主要是画不出来的高频纹理**（发丝、翅膜、碎玻璃），不是阶跃边界。再把权重推到极端（`--edge-boost 4 --edge-cap 4 --smooth-slack 0.8`：39.8% 像素收紧、m=1.454、容差 4.91→6.11）也只把边带从 31.479 挪到 31.501，全图误差却从 6.843 涨到 7.920。**这个旋钮调的是"在哪切块"，而边带的损失是"这些像素本来就画不出来"，两者不是同一件事。**

**可复用的判据**：开 `--edge-aware` 之前先看「边带 MAE / 全图 MAE」这个比值。接近 1（边带不比别处更难）说明带宽有救，权重值得试；像这张图 5:1，说明边带全是不可重建的高频，**改 `--std` 或分辨率才有用，权重白搭**。§2.13 的"台阶预算只有 0.02～0.06 MAE"是同一个事实的另一面。

**配方定案**：`--preset best` + `--shapes` 时**不要叠 `--edge-aware`**（53 是当前采用版）；要让边缘更清楚，改 `--std` 或分辨率这种直接约束。54 只留 `.lua` 作证据（`（作者本机路径，未随技能分发）`，sha256 `26612951B7…`），**没有出 .gil**——没理由让你真机去试一版注定只是并列的结果。

**顺带钉一条可复现性**：`--shapes` 的**线程数会改变结果**（同一张 320px 合成图：`--shape-threads 1` → 973 控件，`8` → 925，差 5%）。同一条命令、同一线程数两次跑是逐字节相同的，所以 A/B 必须**显式固定 `--shape-threads`**，且两版用同一个值；默认值随机器核数变，跨机器复现会漂移。

## 2.16 画风是一个选项：平涂让形状拟合的收益翻倍（2026-10-18）

**要解决的问题**：同一套 `--preset best`，在细节密集的插画上同画质只省 40%～50%（§2.8），控件数照样上万。还能更省吗？**能，但杠杆不在参数上，在你出图那一侧——把素材画成平涂。**

原理一句话：形状拟合本质是「用椭圆 / 旋转矩形盖住一片**同色**区域」，所以**图里有多少平坦区，形状就有多少活干**。

**实测（离线模型，320×448，二次元平涂立绘；从 720×1008 视频取单帧后缩到这个尺寸）**：

| 版本 | 控件 | MAE | STD / 备注 |
|---|---|---|---|
| 原帧 → 纯矩形 | 5,555 | 1.45 | 4 |
| 原帧 → 16 色平涂 → 纯矩形 | 3,568 | 1.48 | 6 |
| 同上 → 分层纯矩形（`--preset best` 的内部基线） | 2,529 | 1.47 | = 2,528 块 + 1 个均色底板 |
| **同上 → `--preset best`（光斑 + 形状）** | **695** | **0.70** | — |

`--std` 是**按「扫到 MAE≈1.5」各图各选一档**（原帧 4、16 色 6），不是同一个值——比的是**同一画质档位下的控件数**。复现：

```bash
python scripts/rect-merge/estimate.py --input ref_raw.png --size 320x448 --scan-std 2,3,4,5   # → 5,555 @ 1.45（STD 4）
python scripts/rect-merge/estimate.py --input ref_q16.png --size 320x448 --scan-std 3,4,5,6   # → 3,568 @ 1.48（STD 6）
python scripts/rect-merge/compress.py --input ref_q16.png --output out.lua --size 320x448 --preset best   # → 695 @ 0.70
```

两条读法：

1. **平涂只贡献三分之一，形状拟合贡献大头。** 平涂 + 纯矩形 = 3,568（画得简单了，屏幕上还是方块）；再上 `--preset best` 才是 **695**——**对 3,568 少 80.5%，对 `--preset best` 自己的分层基线 2,529 少 72.5%，而且 MAE 比两者都低（0.70 对 1.48 / 1.47）**。不经同画质折算就已经赢了。
2. **同一张图、同一画质档的同口径比较更狠**：16 色平涂纯矩形在 MAE 0.83 要 **5,129** 控件（STD 4），`--preset best` 在 MAE 0.70 只要 **695** —— **同画质少约 86%**（0.70 比 0.83 还准，所以 86% 是下界）。换成 4 色量化档：纯矩形 MAE 0.80 要 2,476，形状 695，约省 72%（跨量化版本，只能当近似）。

对照 §2.8 记的 43%～49.5%（256×256、细节密集、同 MAE）：**同一个工具，平坦图上的同画质节省到约 86%，接近它的两倍。**

**物理原因是平坦区占比**（3×3 邻域全同色的像素比例）：这张图原帧 44.5%，16 色平涂后 78.5%。平坦区越多，λ 判据下「一个形状能取代的矩形」越多。`--spotted` 吃这条更狠——§2.8 已经记过「平滑插画 R2 省 15.8%～29.2%，细节插画 R1 只省 5.1%～5.7%」，同一个机制。

**画风配方**：

| 要 | 不要 |
|---|---|
| 大色块平涂，一个部位 2～4 个色阶 | 照片式无限色阶、写实渲染 |
| 干净边缘（**抗锯齿交给形状本身提供**） | 噪点、胶片颗粒 |
| 少量柔和渐变交给光斑层（`--spotted`） | 大面积复杂渐变 |
| 色数 ≤ 16～32 | 上万色 |

**会吃掉收益的内容**（先估再决定）：一根根画出来的发丝、书页文字、布料 / 木纹这类高频纹理。定量判据用 §2.15 的「边带 MAE / 全图 MAE」比值：接近 1 说明边带有救；像 5:1 那样说明边带全是画不出来的高频——**画风也救不了，改分辨率或预算是正解**。

**命令**（其余与 §0 完全相同）：

```bash

python scripts/rect-merge/compress.py --input 16色.png --output out.lua --std 5 --size 320x448 --preset best
node scripts/rect-merge/preview.mjs out.lua 预期效果.png    # 重点看斜边 / 发丝是不是变成了平滑曲线

# 编进关卡：底关卡不用向用户要，用官方 3.21 示例（§2.7 也推荐它）

node scripts/rect-merge/to-gil.mjs out.lua --seed references/samples/mh47p30a87qo_客户端脚本.gil \
    -o 图.gil --unit 2 --default-layout-only

```

平坦图上 `--std` 对控件数**不敏感**（320×448 上 STD 4～6 的差异落在噪声里），先粗定一档，再用 `--shape-strength` 收口。

**顺带把锯齿一起解决**：§2.11 的结论是「补条改变不了台阶，杠杆在分辨率和控件数」。平涂 + 形状走的是第三条路——**控件少了 5 倍，但每条边界由抗锯齿的椭圆 / 旋转矩形画出来，阶梯换成了平滑曲线**。同一张图的目视对比：纯矩形版发丝、眼睛、腮红边缘全是方阶；形状版是连续曲线。

**与流畅度的关系**：§6.1 的【第三方】稳态开销是「可见控件数 × 15~18 µs」——4 万控件 ≈ 1.5 fps，3,568 ≈ 17 fps。**但 695 这一档别再写成「≈87 fps」：真机实测 695 个可见控件跑 60.5 fps，而那是引擎的帧率上限**（0 可见与 695 可见同帧时间，见 §6.1.3）——**引擎封顶 60 fps，超过 60 的外推一律不可观测**。存档**实测 0.36 MiB**（见下方限制），占 20 MiB 上限约 1.8%。**这是少见的能同时改善「控件数 / 锯齿 / 存档体积」三件事的旋钮**——其余旋钮（`--std` / `--shape-strength` / 分辨率 / `--edge-aware` / 补条）都是在拿其中一个换另一个。

**限制**：

- **全部离线**：单帧、单个分辨率、一次运行，**未真机验证**，MAE 是带覆盖率混合的模型值。探针产物在本机临时目录（不随技能分发）。
- **形状占比极高，建立时间未知**：695 个控件里只有 **63 个**是普通矩形，其余 632 个是形状（含旋转矩形），**其中 609 个带旋转**（2026-10-18 成品回读）。按 §2.8 的【真机】每次 `SetLocalRotation` 约 10 ms，**若 609 个都调一次就是约 6 秒的开局停顿**——而 §6.1 的线性估算（0.223 ms/控件）只给 0.16 秒，两者差 37 倍。**本技能没测过「几百个形状」这个量级**的建立时间，这是本条最大的未知。
- **怕开局停顿就用 `--shape-no-rotation`**（2026-10-18 实测替代档）：**756 控件、MAE 0.84、带旋转的 91 个**（估算 `SetLocalRotation` 从约 6.1 s 降到约 0.9 s）。实测这个开关的作用范围**比名字大**：旋转矩形、三角形、圆环三类全部归零（三角 200→0、圆环 45→0），椭圆从 243 涨到 663 吃掉了预算，总旋转数 609→91；**但仍有 91 个旋转**，与 §2.11「只出不旋转的椭圆」的说法**对不上**，机制未查清 —— 所以**别假设它等于 0 次 `SetLocalRotation`**。代价：控件 +9%、MAE 0.70→0.84。两档都出了成品，见下方实测。
- **成品存档体积已实测（离线编码，未真机打开）**：695 控件 → **372,524 字节（0.36 MiB，`to-gil.mjs` 估算编辑器记 0.37）**，占 20 MiB 上限 **1.8%**；`--shape-no-rotation` 档 756 控件 → **0.38 MiB**（编辑器约记 0.40）。两档 `verify-gil.mjs` 回读都 **空洞 0 / 差异 0 / 重叠 0**：旋转档 695/695、maxDiff **0.32**（旋转 609 / 椭圆 243 / 三角 200 / 圆环 45 / 半透明 315）；无旋转档 756/756、maxDiff **0.41**（旋转 91 / 椭圆 663 / 三角 0 / 圆环 0 / 半透明 357）。两档 `gi.mjs verify` 均 **0 error / 0 warn**。**但「能编码」不等于「能打开」**，真机仍待验。

- **别只改画风不换路径**：那样只有 −36%，而且屏幕上还是方块。**两条要一起上。**

## 2.17 动态内容（视频 / 序列帧）的控件安排（2026-10-18）

静态图的结论**不能直接平移到视频**：静态只算「控件数 × 单价」，动态多出「每帧改多少」的开销，而且**镜头切换会让单套几何整体失效**。

**实测样本**（720×1008、27.98 s、972 帧、34.74 fps 的手绘动画，降采样到 320×448 拟合）：

| 项 | 实测 |
|---|---|
| 硬切 | **82 次 → 83 个镜头** |
| 镜头长度 | 19 个 1 帧、19 个 2 帧、**45 个 ≥3 帧（覆盖 94% 的帧）** |
| 帧间变化（中位） | 亮度差 0.54/255，**变化像素 1.9%** |
| 完全重复帧 | **195 帧** |

**帧间只动 1.9%**，所以「每帧重建全部控件」浪费极大，该做**门控**（颜色没变就不写）。

### 成本模型：三项开销，缺一项就会算错

```
每帧开销 = 可见控件 N × 16.5 µs + 隐藏控件 T × 1.7 µs + 改色/改几何 W × 1.9 µs
存档      = 控件总数 × 481 B + 488,445 B  ≤ 20 MiB（≈ 40,800 控件；481 B 为【实测·本机】，见 §2.18）
```

**三项的证据等级完全不同，别混着信**：第三项（`W × 1.9 µs`）**已真机实测**（2026-10-19：位置 1.92 / 尺寸 2.04 / 改色 2.11 µs，30 遍复测，见 §6.1.1），原按 12 µs 算是**高估约 6 倍**；第一项（16.5 µs）**v2 与 v3 两轮探针都没验成**——v2 方法错（把撞上限的段也拿去平均），v3 的二分发现 **0 可见与 695 可见同帧时间、根本没有交叉点**，只拿到区间 **2.4～17.8 µs**，第三方数没被排除也没被证实（见 §6.1.3）；第二项（1.7 µs）**仍是第三方，一次没验过**。第一项才是每帧主项：N=1400 时它贡献 23.1 ms，改写只贡献 0.58 ms。**下面所有 fps 数字，命门都在那个还没测准的 16.5 µs 上。**

**而且引擎封顶 60 fps**（真机基线 16.53 ms = 60.5 fps，0 可见与 695 可见都是这个数）。**任何超过 60 fps 的估算都不可观测**——这张表用来比较两种路线的相对开销可以，用来预测「能跑多快」会误导。

**还有一个不在这个模型里的开销：改几何的帧末重建（§6.1.2）。** 真机 695 个控件全改几何，脚本侧 11 ms，帧末**再加约 1 ms**（最坏单帧 4.5 ms）。这一项曾被 v2 的污染数据估成 230 ms、被 v3 推翻。这个模型算的是「每帧稳态」，**算不出换镜头那一下的卡顿**——两个问题必须分开算，而本关的答案是**不卡**。

**第二项最容易漏：隐藏控件不是免费的，约是可见的 1/9。** 于是「每个镜头做一套、用哪套显示哪套」这种最自然的写法会反噬——83 套 × 700 控件，光隐藏开销就 **98.8 ms/帧（≈9 fps）**。

### 四种安排实测（每镜头 N=700，全片 972 帧）

| 方案 | 控件总数 | 每帧 | fps | 全片 MAE |
|---|---:|---:|---:|---:|
| 一套几何跑全片 | 700 | 12.3 ms | 81 | **19.67** |
| 16 套全挂着 | 11,200 | 30.5 ms | 33 | 13.18 |
| 83 套全挂着 | 58,100 | 111 ms | 9 | 6.91 |
| **83 套双缓冲（只留 2 套）** | **1,400** | **14.5 ms** | **69** | **6.10** |

**结论：几何按镜头分套，但只保留 2 套**（一套显示，一套在空闲帧改写成下一镜头的几何）。这是唯一同时改善流畅度与质量的做法——比「83 套全挂」快 7.6 倍，质量一样。

另外两个必做的优化（都实测有效）：

1. **联合拟合**：每镜头的几何用镜头内 3～4 帧联合最小化方差，而不是只拟中间帧 → MAE **7.68 → 6.10**
2. **改色门控**：颜色变化 < 3 的控件不写 → 每帧改写从 700 降到 **145**（省 6.7 ms）

### 质量 / 帧率交换曲线（双缓冲 + 每镜头几何，全片 972 帧）

| N/镜头 | 全片 MAE | 每帧改写 W | 每帧 | fps | 存档 |
|---:|---:|---:|---:|---:|---:|
| 300 | 8.44 | 55 | 6.1 ms | 163 | 282 KB |
| 500 | 6.94 | 100 | 10.3 ms | 97 | 470 KB |
| 700 | 6.10 | 145 | 14.5 ms | 69 | 658 KB |
| 1000 | 5.29 | 214 | 20.8 ms | 48 | 940 KB |
| **1400** | **4.63** | **304** | **29.1 ms** | **34** | **1.3 MB** |

**存档完全不是瓶颈**（N=1400 才 1.3 MB，占 20 MiB 的 6.5%）——**卡的是每帧可见控件的绘制开销**。这和静态图正好相反，别把 §2.7 的预算公式当唯一约束。

45 套几何的重写成本：每镜头 1,400 × 4 属性 × **2.0 µs（真机实测）≈ 11.4 ms** 是**脚本侧**的账——原按 12 µs 估的 67 ms 高估 5.9 倍。引擎侧的帧末重建：真机 695 个全改是 **约 1 ms**（最坏单帧 4.5 ms，§6.1.2），按线性外推到 1,400 约 2 ms。**两项加起来换镜头约 13 ms，不构成瓶颈。**（v2 曾报 230 ms，那是同一帧里积压了 8.6 万次写的污染值，已被 v3 推翻。）

**帧末重建的量级已经测出来了（约 1 ms、最坏 4.5 ms），三种解释（一次性 / O(N) / 每次全量）在本关都落在这个范围里，因此不必再分辨**——长镜头（占 94% 的帧）靠空闲帧吸收，1～2 帧的短镜头直接借用最邻近长镜头的几何，都成立。

### 全片效果与它的天花板

按 N=1400、45 套几何渲染全部 972 帧：全片 **MAE 5.02**（中位 4.54、p90 7.53），每帧改写 301 个控件、**34.4 fps**，存档约 **1.3 MB**。

**目视结果：结构、配色、表情都对，但整体是块状的**——眼睛高光、发丝边缘被切成方块。原因是 1400 控件 ÷ 143,360 像素 = **102 像素/控件**，对带高光与分层发丝的插画不够。

- 静态图能到 MAE 0.70，代价是 **27,509 控件**
- 视频里 27,509 控件 = **454 ms/帧 = 2.2 fps**

**所以「质量」与「流畅」是硬冲突，不是调参问题。** 目前最好的交换是 N=1400 / 34 fps / MAE 5.02。

**限制**：

- **改写单价已真机校正，但帧率仍只是模型值（2026-10-19）**。几何写 1.68～2.40 µs、改色 1.92 µs 是【真机实测】（§6.1.1），原 12 µs 高估约 6 倍；**但 16.5 / 1.7 µs（可见 / 隐藏控件的稳态渲染开销）仍是【第三方】（481 B 已在 2026-10-18 升为【实测·本机】，见 §2.18），而 16.5 µs 才是每帧主项**。v3 的二分也没能量出它——0 可见与 695 可见同帧时间，本关 695 个块全都装得进 60 fps 预算（§6.1.3）。所以上面几张表的 fps 列**故意不改**——重算只会得到一个末两位都在抖的数。
- **引擎封顶 60 fps，这是所有 fps 外推的天花板**：真机基线 16.53 ms = 60.5 fps。**任何写着「>60 fps」的估算都不可观测**，只能读作「装得下」。
- **「几何重写」这个地基：三个子问题已答两个**（2026-10-19 真机）。① 能不能改 x/y/w/h？**能**，12 项能力探测全 OK。② 每属性多贵？**1.68～2.40 µs**，不是 12 µs。③ **「改尺寸会不会触发画布重建」仍未测**——探针在 `OnStart` 跑，一帧没渲染，量到的是调用成本；1400 个 RectTransform 一起改，Unity 的 Layout/Canvas 重建发生在**帧末**，成本不在探针的秒表里。这一项只能靠「改完几何后下一帧的 dt」来量（探针 v2 的对应段）。**在它量出来之前，双缓冲的结论是「API 已通、帧末代价未知」**，不是「已成立」。备选仍是「K=16 全挂着」（MAE 13.18 / 33 fps），质量更差。
- **几何在 320×448 上拟合、显示时放大**，放大后的实际观感没有单独评估。
- **形状在动态内容上不成立（2026-10-18 实测，3 个镜头）**：单帧拟合时形状极准（拟合帧 MAE 1.30～1.58，`--preset best` 约 600 s/帧），但**一有运动就崩**——镜头内均值反而输给矩形。**同控件数**对照：

  | 镜头 | 帧数 | 控件数 | 形状均值 | 矩形（同控件数） | 胜 |
  |---|---:|---:|---:|---:|---|
  | 80 | 152 | 2,887 | **5.22** | **2.45** | 矩形 |
  | 5 | 6 | 2,542 | **3.01** | **2.32** | 矩形 |
  | 70 | 3（近乎静止） | 4,569 | **1.58** | 1.98 | 形状 |

  原因：矩形是规则网格，小位移只影响块内颜色（每帧重采一次就够）；形状是**贴着某一帧边缘拟合的大块**（平均覆盖约 440 像素），内容一动就整块错位，而边缘又锐利，错位代价远大于网格的模糊代价。**所以「静态图优先形状、动态内容优先矩形」是正确分工**，不要因为 §2.16 的单帧结论就把形状搬到视频上。只有镜头本身接近静止（帧间亮度差 < 0.05）才值得换，收益约 20%，而每镜头拟合约 600 s，不划算。
- **镜头内漂移是主要误差来源**：只拟首帧时，长镜头末段 MAE 会从 1.30 涨到 5.54（镜头 80，152 帧）。矩形靠「镜头内 3～4 帧联合拟合」把这件事压住了；换成形状则没有等价手段（`compress.py` 只能拟合单图）。

### 2.17.1 端到端落地：约束从「存档 / 帧预算」翻到「脚本体积」（2026-10-19）

上面 §2.17 是**离线模型**的账。真按它做一份能进关卡的成品时，**瓶颈换了两次**，最后卡在一个之前没人算过的量上。

**成品参数**：320×448 源帧 → **1400 块**、**972 帧**、**24 段几何**、18 bit 色。源视频硬切候选 158 个（`med + 5·MAD` 阈值）按「相邻两段总长最短」贪心合并到 24 段。

| 段数 K | 全片 MAE | 几何字节 | 说明 |
|---:|---:|---:|---|
| 1（全局） | 8.70 | 0 | 一套几何跑全片 |
| 24 | 5.62（未量化） | 197 KB | **成品选这个** |
| 30 | 5.36 | 246 KB | 体积撑不住 |
| 36 | 5.18 | 295 KB | 体积撑不住 |
| 每帧自拟合 | **3.16** | — | 理论下界，不可实现 |

**三个瓶颈排队出现，顺序和直觉相反：**

1. **存档（20 MiB）完全不是问题**：1400 块只有 0.69 MiB。
2. **帧预算也不是问题**：普通帧约 250 块改色 ≈ 0.5 ms，换段帧 1400×4 次几何写 + 1400 次改色 ≈ 14 ms，而 34.74 fps 的预算是 28.8 ms。
3. **真正卡住的是 Lua 脚本体积**：`§6` 的平台边界里有两条真机数据点——**1.23 MB / 6.2 万个表构造器能正常加载，2.01 MB 无任何日志（编译期失败）**。这直接把「45 套几何 + 24 bit 色」的模型方案（约 1.9 MB）判死，只能降到 24 段 + 18 bit 色，**端到端 MAE 7.01**（中位 6.55、p90 9.99）。

**所以动态内容的第一约束是「脚本里能塞多少字节」，不是控件数。** 规划时先算 `几何 + 颜色轨道` 的字符数，再倒推 K / N / 色深。

**轨道编码（实测字符数）**

| 段 | 内容 | 字符数 |
|---|---|---:|
| 几何 | 每块 6 字符 = `((x*448+y)*320+(w-1))*448+(h-1)`，36 bit | 8,400/段 × 24 = 201,600 |
| 颜色 | 每帧头 3 字符（条目数）+ 每条目 1～3 字符索引差 + 3 字符 18 bit 色 | 969,900 |
| 段表 | 每段 3 字符起始帧 | 72 |
| **合计** | | **1,144 KB**（脚本 1,149 KB） |

- 颜色条目 **241,257**（平均 248/帧）。阈值 `TH=6` 时条目数约为 `TH=3` 的 0.68 倍，肉眼无差。
- 索引差从 **-1** 起算（`dv = i - last`，`last` 初值 `-1`），≤62 用 1 字符，更长用 `63 + 2 字符`。
- 字母表用 `byte = 48..92, 94..112`（**剔掉 `]`**），这样数据永远不会出现 `]]`，可以直接放进 `[[...]]`；解码 `b > 93 and b - 49 or b - 48`。

**两个必须记住的坑（都是自己写出来的）**

1. **索引差的基点是 -1，编码端和解码端必须一致。** 编码端 `last = -1`、解码端 `last = 0` 会让每条记录右移一位：绝大部分块偏一格看不出来，**最后一条会越过 N 直接越界**。这次就是这么发现的（IndexError: 1400）。
2. **增量的颜色必须有持久表。** 每帧新建一个 `zeros(N)` 再叠增量，只会渲染出「本帧改过的块」，其余全黑。Lua 端的 `CUR[i]` 和离线校验端的 `CUR` 都必须是**同一张跨帧保留的表**。

**验证方法：模拟器不够，必须离线复算一遍。**

`sim-lua smoke` 对颜色类 bug **完全不敏感**——解码器带上面第 1 个越界 bug 时，smoke 依然报 0 错误（越界被 `if c ~= nil` 吞掉）。可靠的做法是**用 Python 把 Lua 的解码逻辑原样重写一遍**，还原 972 帧、逐帧对源像素算 MAE，并断言「轨道读指针正好读完」（本次 969,900 / 969,900）。

**运行时两个实现细节**

- **追帧要分「写」和「不写」**：卡顿后要在一次 `OnUpdate` 里补若干帧，中间帧只更新 `CUR`、不写控件（`applyFrame(skip)`），最后一帧才写；否则补 8 帧就是 8 倍的 API 开销。
- **循环回绕要重放第 0 帧**：轨道是线性的，回绕时把读指针、段指针一起复位并重新应用几何 0 + 全量颜色。

### 2.17.2 帧间相关性还剩多少可挖（2026-10-19 实测，全解码口径）

对上面那份 972 帧成品**把 TRK 完整解码**后测量，不是抽样、不是代理：

| 量 | 实测 |
|---|---|
| 颜色条目总数 | **241,257**（普通帧均值 221.5 / 中位 110 / P90 619，全量刷新帧只有 1 个） |
| 段切换帧 | 24 帧，均值 **1,305 条**，**占全部条目的 13.0%** |
| 全片不同 18bit 色 | **11,878** |
| 变化条目的颜色熵 | **11.52 bit**（定长用 18 bit） |
| 索引差熵 | **2.22 bit**（定长用 6 bit） |
| 位置 + 颜色下界 | **13.74 bit / 条**（现在用 24 bit） |
| → 纯编码浪费 | **43%** |

**但这 43% 是熵编码冗余，不是「帧间冗余」。** 两条独立的证否：

- **时间预测无效。** 用「上一帧同块的颜色」当预测器，**残差熵 22.22 bit > 绝对熵 10.94 bit**；变化条目里新颜色恰好等于前 1/2/3/8 帧同块的比例只有 **0.00% / 0.40% / 0.75% / 1.18%**。运动把块内颜色彻底打散，**相邻帧同块的颜色几乎不可预测**——运动补偿 / 差分预测这条路可以一句话排除。
- **空间局部性才是真的。** 索引差熵 2.22 bit、99.3% 的 dv ≤ 62——变化的块成片成簇，这部分能压。

**按频率排序的变长色码**（64 符号字母表，1/2/3 字符前缀无关码）能把 **4.02 字符/条压到约 2.91**，省 262 KB；扣掉 11,862 色的秩表（35 KB）**净释放 227 KB，且无损**。

**227 KB 买得到什么（实测换算）**

| 用途 | 单价 | 换算 | 画质 |
|---|---:|---|---|
| 加段数 | 每段 = 8,400 几何 + 1,305×4 切换条目 = **13,620 字符** | +17 段（K 24→41） | MAE −9% |
| 加块数 | — | N 1400→**1735**（+24%） | MAE −7% |

块数的画质指数是实测的：**N×2 → MAE ×0.807**（N=700 时 10.77 → N=1400 时 8.70，同一全局几何口径）。

**结论：这条线已经过了拐点。** 43% 的编码浪费只换回 7%～9% 画质，因为 K 和 N 双双处在收益递减段。真要再上台阶，需要的是**让几何在时间上连续**——持久四叉树、每段只记分裂/合并的 delta，把 8,400 字符/段的几何降到几百字符，才能把 K 推到接近逐帧。那是另一个项目，不是调编码参数。

**方法教训**：判断「帧间有没有相关性」不要凭直觉，先把**残差熵和绝对熵并排放**。本次残差熵是绝对熵的两倍，一行数就关掉了整条预测路线。

### 2.17.3 熵编码落地 + 层叠图元对照（2026-10-19 实测，972 帧全程离线还原）

**v2 编码（已实现，端到端跑通）**

| 项 | v1 | v2 |
|---|---|---|
| 颜色 | 定长 3 字符（18 bit） | 64 进制 canonical 变长码，**2.038 字符/条**（m1=10 / m2=3313 / m3=9095） |
| 索引差 | 定长 1 字符（6 bit）+ 3 字符逃逸 | 位打包 canonical Huffman，**平均 2.16 bit**（最大码长 18） |
| 帧头 | 3 字符 | 11 bit，并入位流 |
| 新增开销 | — | 颜色表 12,418×3 = 35,634 字符；码长表 1,400 字符 |
| 两条流 | 单流 | **颜色走字符流、索引差走位流，两条独立的流**（游标各自维护） |

同段数 K=24：**1,171,456 → 824,248 字符（−29.6%），MAE 完全不变（5.62 → 5.62）**。
把这 339 KB 全部换成段数（K 24→52）：理想 MAE **5.62 → 4.66（−17.1%）**，端到端 **7.01 → 5.97（−14.8%）**，
**而脚本反而小了 5,333 字节**（1,176,190 → 1,170,857）。

**三个实现坑（都踩过，`sim-lua` 全都测不出来）**

1. **字母表必须剔掉 `]`**（字符 93），否则 `[[...]]` 长串被数据截断。用 `48..92, 94..112`。
2. **canonical 码的 firstcode 递推**是 `cur = (prev + cnt[L-1]) << 1`，**循环里不要再 `+= cnt[L]`**——写错会让整个码本平移，脚本照样跑、不报错。
3. **Huffman 堆里必须存节点下标而不是符号下标**：`freq == 0` 的符号被跳过时两者不等，会 `IndexError`。
4. 解码正确性只能靠**离线复算**：本次断言「颜色流指针正好用完、位流正好读完」，两个 bug 都是它抓的。

**色深：18 bit 是实测最优点，24 bit 反而更贵**

| 每通道位 | 不同色 | 颜色表 | 颜色流 | 颜色总成本 | 端到端 MAE |
|---:|---:|---:|---:|---:|---:|
| 6 bit（18） | 12,418 | 37 KB | 572 KB | **609 KB** | 5.97 |
| 8 bit（24） | **133,555** | **522 KB** | 785 KB | **1,307 KB** | ~4.7（预算内放不下） |

**色深一上去，不同色数爆炸 10.8 倍，颜色表比买到的画质还贵。** 18 bit 带来的 1.31 MAE 量化损失是这套编码的「固定税」。
想消掉它得换**学习式调色板**（P 个真实高频色 + 最近邻映射）：P=16k 时颜色表 4 字符/条 ≈ 64 KB、码本熵略升，
预计能拿回大半而只多花约 45 KB —— **未实测，下一轮首选项**。

**C：层叠图元（fogleman/primitive 风格）——同形状数下分区矩形全档位胜出**

自写纯 numpy 拟合器（本机无 Go / ImageMagick）：椭圆 / 旋转矩形 / 三角形 + 半透明 + 画家算法，
颜色闭式解 `col = mean(C) + mean(T−C)/α`，误差加权采样 + 爬山。帧 0 实测：

| 形状数 | 分区矩形 MAE | 层叠图元 MAE |
|---:|---:|---:|
| 40 | **9.48** | 12.31 |
| 100 | **7.09** | 8.24 |
| 200 | **5.51** | 5.74 |
| 400 | **4.07** | 4.27 |
| 1400 | **2.28** | — |

**数据成本才是致命的**：一条图元定长 61 bit ≈ 10.2 字符，**而且每帧都要发**；矩形几何只在换段时付一次（8,400/段）。

| 口径 | 400 图元 × 972 帧 |
|---|---:|
| 每帧全量重发 | **3.77 MB** |
| 帧间增量（实测 76.8% 位移 / 61.5% 改色） | **2.61 MB** |
| 1.23 MB 脚本预算内能放 | 131（全量）/ 188（增量）个/帧 |

按实测曲线 188 图元 ≈ MAE 6.0，**只是与 v2 打平**；且**帧间不稳定**（暖启动后仍有 76.8% 的图元每帧位移 > 1 px），
风格化观感见 `（作者本机路径，未随技能分发）`。
**结论：在「接近原图」这个目标下不划算；它的价值在可编辑性（每个图元是真实形状），不在画质。**

**方法教训**：比较两种表示法必须**同形状数**、且**把帧间成本算进去**。只看单帧 MAE 会得出「图元更省」的错误直觉——
实际上图元在每个档位都更差，而每帧的数据量还是矩形的 2.4 倍。

### 2.17.4 画质天花板在脚本体积：三个真正的杠杆（2026-10-19 收工版，972 帧全解码口径）

用户反馈「画质太差」后重做的三项。**总收益 5.97 → 4.70（−21%），脚本从 1,171,481 B 降到 1,127,642 B。**

**① 换块判定口径 —— 单条最大收益（−0.61 MAE，且不用多花一个字节就能同时变小）**

旧口径是「本帧真值 vs 上一帧真值」，新口径是「**本帧真值 vs 当前画面上那个块的颜色**」。

> 旧口径下，一个块每帧漂移 1 个单位永远不触发写入（每步都 < TH），**误差无界**。
> 新口径把渲染误差硬性锁在 TH 以内。

| 口径 | 条目 | 总字符 | MAE | max |
|---|---:|---:|---:|---:|
| 上一帧真值 | 371,670 | 1,161,308 | 5.078 | 7.95 |
| **当前画面色** | 393,946 | 1,267,473 | **4.472** | 7.49 |

**这是纯编码端改动，解码端与数据格式完全不变。** 凡是「只在变化时写」的逐帧方案都该这么写。

**② 几何按切割树编码 —— 6.43× 压缩，把预算从几何挪到别处**

分区本来就是 `fit_rects` 递归切出来的（每次一刀、切某一侧的整条边），所以它天然是一棵**切割树**：
每个内部节点只要 **1 bit 方向 + ⌈log2(跨度−1)⌉ bit 位置**，叶子坐标由路径推出，不必逐块存 6 字符。

| | 每块 6 字符 | **BSP 切割树** |
|---|---:|---:|
| 每段（N=1400） | 8,400 字符 | **1,774 字符**（含叶/分裂标记 2N−1 位） |

> **漏算过一笔**：只数「方向 1 bit + 位置位」会得 1,307 字符，但解码器得知道哪一步是叶子，
> 还要 **2N−1 位的叶/分裂标记**（+466 字符/段）。建 Lua 前一定按 3N−2 位算。

解码用显式栈 + 4 条并列数组（`SX0/SY0/SX1/SY1`）前序遍历，叶子按前序分配块号，**和编码端 DFS 顺序必须逐位一致**。

**③ 拟合采样数 —— 几乎免费的画质（−0.38 MAE / +2.7 万字符）**

每段拟合只取 3 帧是**严重欠采样**。同预算下把采样提到 16 帧：

| 每段采样 | 3 | 8 | 16 | 全部（24 上限） |
|---|---:|---:|---:|---:|
| MAE（K=52, N=1400） | 5.872 | 5.521 | **5.495** | 5.497 |
| 总字符 | 759,437 | 786,191 | 788,518 | 790,361 |

**16 帧就饱和**，再往上无收益。长段尤其重要。

**配置前沿（N=1400，18 bit 色，全帧采样）**

| K | 条目 | 总字符 | MAE | p90 |
|---:|---:|---:|---:|---:|
| 52 | 305,787 | 814,593 | 5.497 | 6.88 |
| 110 | 351,647 | 1,001,739 | 5.177 | 6.80 |
| 158 | 371,670 | 1,119,928 | 5.078 | 6.80 |

**K 的上限是镜头数（本例 158）**——`merge_to` 只能合并镜头、不能切，想要更多段必须换「任意边界 + DP」的分段器。
K 超过 ~110 后收益已经很小（+48 段只换 −0.1）。

**N 与 K 的成本结构（决定该往哪投）**

- 几何 ≈ **0.93 字符/块/段**（BSP）；颜色 ≈ **2.07 字符/条目**
- 条目 ≈ `K×N`（换段全量刷新）**+ 段内变动**，所以 **N 翻倍 ≈ 总成本翻倍**；K 翻倍只加几何 + 刷新
- 实测 N×2 → MAE ×0.807；K 24→52 → ×0.829。**两者都在迅速饱和**，因为这段视频帧间运动极快
  （每帧自拟合下界 3.16，而 4.6 帧共用一套几何就已经是 4.9）

**试过但没用的**

| 试的 | 结果 |
|---|---|
| 换段时**不做全量刷新**、只写超阈值的块 | 条目 405,950 → 393,946（只省 3%）：分区变得够多，DFS 同序的块颜色也基本都变了 |
| 24 bit 真彩 | 不同色 12,418 → 133,555，颜色表 37 KB → **522 KB**，超预算 57% |
| 帧间颜色预测 | 残差熵 22.22 bit > 绝对熵 10.94 bit，**命中率 0.00–1.18%**（§2.17.2） |
| 提高 K 到 158 以上 | 不可能（镜头数上限），且已饱和 |

**阈值量化陷阱**：颜色按 `(q<<2)+2` 还原，三通道差全是 **4 的倍数**，所以 `TH=5/6/7/8` 完全等价（都等于「差 ≥8」），
`TH=9/10/11/12` 等价于「差 ≥12」。想要细粒度得换成 L1 和之类的判据。

### 2.17.5 误差三分：几何地板 / 量化 / 时间陈旧（2026-10-20 实测）

**先做这件事，再谈优化。** 把端到端 MAE 拆成三项，才知道还有多少可压。N=1400 / K=158 全解码口径：

| 口径 | MAE | p90 | 含义 |
|---|---|---|---|
| **每帧全量、精确块均值** | **3.867** | 4.86 | **几何地板**——1400 块再怎么编码都下不去 |
| TH=4 精确色 | 4.018 | 5.06 | 只含时间陈旧 |
| TH=8 精确色 | 4.236 | 5.29 | |
| TH=12 精确色 | 4.513 | 5.69 | |
| TH=4 18 bit | 4.265 | 5.20 | 加 6 bit/通道量化 |
| TH=8 18 bit | 4.472 | 5.46 | |
| TH=12 18 bit（v3） | 4.704 | 5.84 | 当前交付 |

**三条可复用的结论：**

1. **几何地板才是真天花板。** 1400 块的地板是 **3.867**，而 v3 是 4.704——**能压的只有 0.84**，
   其中 0.65 是时间陈旧、0.19 是量化。把编码优化到极致也只到 4.0 上下，**加块是唯一能继续降的路**。
2. **量化代价 0.19–0.25**（4.513→4.704），比想象的小；24 bit 已证不划算（§2.17.4），
   所以「换更高色深」这条线收益上限只有 0.25，别再花力气。
3. **TH 的边际收益递减得很快**：12→8 用 145 KB 换 −0.23；8→4 用 **452 KB** 只换 −0.21。
   `TH` 每降一档多花的字节数翻倍。

**加块降的是地板，不是便宜货**（同一口径，S=3 拟合，偏保守）：

| N | K | 地板 | TH=12 | TH=8 | 条目(TH=12) | 颜色字符 |
|---:|---:|---:|---:|---:|---:|---:|
| 1400 | 158 | 3.867 | 4.705* | 4.472* | 331,832 | 688,570 |
| 2000 | 110 | 3.610 | 4.446 | 4.217 | 442,846 | 918,905 |
| 2800 | 90 | **3.192** | 4.109 | 3.867 | 603,689 | 1,252,654 |

\* 这两格是 S=24 拟合，另两行 S=3，所以 1400 行反而略优——**横向比只能看「地板」和「同 TH 的相对差」**。
地板从 3.87 掉到 3.19（N=2800），但颜色数据也翻倍：**同字节预算下，加块只比降 TH 略优**。

**因此：预算固定时 MAE 大致落在 4.0–4.3，加块与降 TH 换不出质变；真正的门槛是脚本能多大。**
`20 MiB` 是**存档总量**上限（本关 `.gil` 0.69 MB + 脚本 1.73 MB = 2.4 MB，只用了 12%），
和脚本加载上限是两回事，别混。旧证据「2.01 MB 失败」是 **8.9 万个表构造器**的脚本，
本路线是**6 个巨型字符串 + 约 250 行代码**，两者形态完全不同，所以那不是字节上限的直接证据。

**已交付 v4（2026-10-20）**：N=1400 / K=158 / TH=4，脚本 **1,728,752 B**，MAE **4.265**（p90 5.20 / max 7.34），
`verify3.py` 三条流全部正好用完、`sim-lua lint` 0/0/0、`smoke` 1350 帧 0 错误。
同一份 `out/` 里还留了 TH=8 的 **1,275,502 B / MAE 4.472** 作回退。**这版同时是体积探针**：
它比已验证的 1.13 MB 高 40%，能不能加载本身就是关键情报。

## 2.18 评测域与画布密度：固定占位下，密度才是杠杆（2026-10-18 离线，2026-10-20 真机）

静态图这条线前面所有"加控件""收紧 `--std`""换采样核"的实验，最后都撞到同一堵墙。10-18 夜里把评测口径从画布域改到**屏幕实际像素**以后，墙后面的结论翻了：**预算不是杠杆，画布密度才是。** 64 号（800px / unit 1.25）已真机通过。

### 先定显示域，再比较

设备上一张图的占位 = `画布边长 × --unit` 个布局单位（本图 500 × 2 = 1000）；1080p 下 1 布局单位 ≈ 1 个屏幕像素。眼睛看到的是这个**显示域**，不是拟合器自己的画布。

| 名字 | 定义 | 用途 |
|---|---|---|
| 画布域（500 域） | 结果按画布 500×500 量（原生） | 拟合器自己的目标；**不能跨分辨率横比** |
| 2000 域 | 4× 覆盖率几何渲染后量（"几何 J"） | 结构 / 假硬边诊断 |
| **1000 域** | 结果双线性放大到占位 1000，真值 = 源图 BOX 到 1000 | **屏幕口径**，所有跨分辨率比较用它 |
| 面积模型 | 4× 渲染 → BOX 缩到 1000 | 引擎光栅化的忠实模型，用来复核 1000 域排序 |

同一对产物（53：500px，625：unit 1.6，同占位 1000、同参数）在不同域里**名次会翻**：

| 域 | 53（500px） | 625 | 谁赢 |
|---|---:|---:|---|
| 500 域 | MAE **1.298** / SSIM **0.9909** | 3.293 / 0.9610 | 53 |
| 2000 域 | 6.526 / J 5.679 | 6.942 / J 7.506 | 53 |
| **1000 域** | 5.484 / SSIM 0.878 | **4.452** / SSIM 0.916 | **625（−18.8%）** |

原因：unit = 2 时每个画布像素被放大成 2×2 屏幕像素，块边界只能落在偶数像素上，是 2 px 方块台阶且没有亚像素混色；625 的每块只有 1.6×1.6。所以 §2.13 的 51 / 52 否决当年是按"同显示尺寸 500"比的，**按 1000 域重算结论可能不变，但没重跑过**（产物都在，成本低）。

### 预算不是杠杆

`--default-layout-only` 脚本版的存档字节（【实测·本机 2026-10-18】，解析工具见下）：

```
存档字节 ≈ 481 × 控件数 + 488,445
53 : 481 × 27,509 + 488,445 = 13,720,274   ← 与实测逐字节相等
57 : 18,780,394（实测 18,962,881，+0.97%）
36 号（已真机）: 19,710,167（台账文件 18.9910 MiB ≈ 19,913,507 B，+1.0%）
```

- 控件节点 = **473 B 固定开销 + 名字字节数**（名字是 `块N`，每多一位数字 +1 B）；
- **块与形状同价**——形状参数全在 Lua 的 `SHP` 串里，不在节点上；
- 存档 98.62% 是界面控件，Lua 脚本 1.24%，其余 0.14%；
- 27,509 个控件的槽内容全不相同（每个控件带自己的 GUID），"省公共槽"这条路不存在；
- 20 MiB 上限 = 19.19 MiB 文件 ≈ **40,800 个控件**（编辑器口径 = 文件 × 1.0417）。

把预算花满，1000 域只换回一点点：

| 版本 | 控件 | 编辑器 MiB | 1000 域 MAE |
|---|---:|---:|---:|
| 53 | 27,509（67% 预算） | 13.63 | 5.4839 |
| 57 | **38,029（93%）** | **18.84** | 5.3970（−1.6%；2000 域真值口径 6.5263 → 6.4336，−1.42%） |

每 1 MiB 编辑器空间约换 0.28% MAE。**收紧 `--std` 也不买控件**：`--std` 只管块层（73,021 → 60,393 块），最终数量由形状层的 λ 平衡决定；`--std` 4.2 → 3.6 控件 27,509 → 27,005（−1.8%），MAE 持平。要买控件，旋钮是 `--shape-strength`，不是 `--std`。500 px 的"每像素一色"无限控件下界（2000 域真值口径）是 6.159，57 仍差 4.5%——差的是**块内细节**，不是控件不够。

### 画布密度扫描（固定占位 1000，`unit = 1000 / size`）

同参：`--preset best --shape-strength 0.9 --focus focus36 --focus-gain 0.8 --resample box`；`--std = 4.2 × size / 500`。

| 版本 | 画布 | unit | 控件 | 编辑器 MiB | 1000 域 MAE | 面积模型 MAE |
|---|---:|---:|---:|---:|---:|---:|
| 53 | 500 | 2 | 27,509 | 13.63 | 5.4839 | 4.3841 |
| 56 | 625 | 1.6 | 28,060 | 13.91 | 4.4523（−18.8%） | 3.5457 |
| 60 | 700 | 1.4286 | 30,633 | 15.12 | 4.0906（−25.4%） | 3.5281 |
| **62 / 64** | **800** | **1.25** | 28,604 | 14.18 | **3.7166（−32.2%）** | **3.2186（−26.6%）** |
| 65 | 900 | 10/9 ≈ 1.1111 | 26,127 | 12.96 | 3.4768（−36.6%） | 3.1470（−28.2%） |
| **63** | **1000** | **1（整数）** | 28,279 | 14.03 | **2.0496（−62.6%）** | **2.2120（−49.5%）** |

900 / 1000 是 2026-10-20 补跑的（同参，`--std = 4.2 × size / 500`：7.56 / 8.4；构建 4,246 s / 4,953 s，两路并行时测的）。**曲线不是平滑下降，到 1000 px 有一个台阶**：800 → 900 只再降 6.5%，900 → 1000 再降 41%（1000 域 MAE 3.4768 → 2.0496；边带 16.15 → 5.10；SSIM 0.946 → 0.974）。我之前担心"unit = 1 的整数相位会变硬"，**结果是反过来**：unit = 1 时 1 个画布像素恰好 = 1 个布局单位 ≈ 1 个屏幕像素（1080p 口径），块边界不再需要任何亚像素采样，拟合器的目标和屏幕上看到的是同一张网格。900 的 10/9 是无限小数，既没享受到整数相位，又要靠吸附才能回读为 0 差异。

> **别把 1000 px 的 −62.6% 当成对所有屏幕都成立**：1 画布像素 = 1 屏幕像素只在 1080p 附近成立。屏幕缩放到 1440p / 4K 时屏幕上每个布局单位占多个物理像素，1000 px 的整数相位优势会缩小，剩下的是分辨率本身的优势。且该数字是【实测·本机离线模型】；63 号已真机通过（只回报"没问题"，没有与 64 并排比），65 号没上真机。

- **机制**（【推断】，与扫描结果一致）：固定占位下块的平均屏幕面积由预算决定（≈ 35 屏幕像素²，约 6×6，500 和 800 一样）；密度改变的是**边界落点精度**——500 是 2 px 量化，800 是 1.25 px。这也解释了历史上所有"加控件不涨画质"的实验：它们买的是块的大小，而屏幕上的误差主要来自边界落点。
- **能站住的只有两条**：800 明显好于 625（两个模型分别 −9.2% / −16.5%），以及 500 → 800 单调变好。700 在面积模型下与 625 打平（3.528 vs 3.546），单种子波动就是这个量级。
- **unit 最好是整数或 0.25 的倍数**（500/2、800/1.25、1000/1）。800 / unit 1.25 = 5/4，布局坐标是 0.25 的整数倍，数值上干净：`verify-gil.mjs --unit 1.25` 回读 diff 0 / maxDiff 0.44。unit 1.6 / 10/9 这类无限小数下，存档里 float32 的位置 / 尺寸带 ~1e-4 的噪声，**旧版 `verify-gil.mjs` 会因此多报 29 px 差异**（58 号 unit 1.6：29 px、maxDiff 17.35；65 号 unit 10/9：29 px、maxDiff 22.1）。**这是校验脚本的问题，不是打包错误**：2026-10-20 把形状几何先吸附回数据格式本来的 1/4 像素再还原（并给矩形路径的取整加 1e-3 偏置），两处都回读为 diff 0（65 号 maxDiff 0.51），完整自检 126 项通过。
- 625 同预算对比 500 时输在相位上（第四轮）：1.25 倍的非整数比让块边界相位错位。**第四轮报告里的另一条原因"p64 的 511 边长上限把背景拆成 7,207 条带"是读错了日志**：`compress.py` 那行"超宽块拆分: 1 个块…拆成 7207 块"里的 7207 是切完之后**矩形层的总块数**，不是那一块被拆出来的数量。被切的只有一块均色底板，≥512 px 时切成 ≤4 条，多 ≤3 个控件。2026-10-20 已把日志措辞改清楚（"矩形层现共 N 块"）。
- **1000 px 也没有顶到预算**：`--std = 8.4` 下 28,279 控件、14.03 MiB（编辑器口径，上限 20），和 800 px 差不多。要不要再往上（1250 / 1500 px，unit 0.8 / 0.667 反而又变回非整数相位）没有测；占位固定 1000 时，画布超过 1000 px 就是在亚屏幕像素上拟合，大概率白花【推断，没测】。

### 怎么用

```bash
# 占位 1000：画布 800（64 号，已真机），unit = 1000 / 800 = 1.25；--std 按 4.2 × 800 / 500 = 6.72 起步
python scripts/rect-merge/compress.py --input 图.png --output out.lua --size 800x800 --std 6.72 --preset best --shape-strength 0.9
node scripts/rect-merge/to-gil.mjs out.lua --seed 底关卡.gil -o 图.gil --unit 1.25 --default-layout-only
node scripts/rect-merge/verify-gil.mjs 图.gil out.lua --unit 1.25                      # 必须传同一个 --unit
# 现在的推荐（63 号，真机通过）：--size 1000x1000 --std 8.4，to-gil / verify-gil 都用 --unit 1
```

- 换占位或换画布时一律 `unit = 占位 / 画布边长`，并优先挑 unit 是**整数或 0.25 倍数**的组合（500/2、800/1.25、1000/1）。
- 构建耗时（16 核笔记本，默认 8 个搜索线程，2026-10-20 提速后）：1000 px 约 **12 分钟**、400 px 约 2.5 分钟；提速前 1000 px 要约 117 分钟（见 §2.19）。
- 控件数随图变，`--std` 与 `--shape-strength` 照旧要为新图标定一次（≤ 4.0 万）。本图 800 px 只用了 28,604 控件，预算还剩约 30%，但把预算花满只值约 1.5%（上面），不值得为此多跑一轮。
- 比较两个跨分辨率版本：先把各版本都放大 / 缩到**显示域**再量，对照图必须目检对齐（早期 `_cmp1000.py` 把 2500 px 源图的裁切系数误写成 2，生成的对照图根本不是同一块区域，数字没错但图误导人；系数应是 `源图边长 / 域`）。

### 逐像素修复与抗锯齿恢复：上限 0.002 MAE（别重复）

## 2.19 构建提速：1000 px 从 117 分钟到 12 分钟（2026-10-20，输出画质持平）

画布密度（§2.18）把推荐配方推到 1000 px 以后，构建要 **116.6 分钟**（63 号）。这一节记下怎么把它压到 **11.8 分钟**（同图、同参数、同 `--std 8.4`）。三段耗时的原始分布与各项改动的效果：

| 阶段 | 63 号（改前） | 66 号（光斑 + 几何 + 光栅化） | 68 号（再加分块并行精修） |
|---|---:|---:|---:|
| 先铺 150 个光斑（单线程） | 2,045 s | 87 s | **72 s** |
| 形状搜索（3 遍，8 线程；63 号是 3 线程） | 2,952 s | 474 s | **424 s** |
| 精修（修剪 / 矩形边 / 几何 / 颜色，单线程） | 1,984 s | 316 s | **190 s** |
| 合计（含少量固定开销） | **6,998 s（116.6 min）** | 915 s（15.3 min） | **706 s（11.8 min）** |
| 控件数 / 构建 MAE | 28,279 / 2.067 | 28,363 / 2.067 | 28,555 / 2.058 |
| 1000 域 MAE / 面积模型 MAE | 2.0496 / 2.2120 | — | 2.0396 / 2.2052 |

63 号用 `--shape-threads 3`，66 / 68 号用默认线程数（`min(8, 核数 − 2)`）。400 px 同样跑一遍：738 s → 146 s（5.0×），24,550 → 24,656 控件、MAE 1.169 → 1.159。**画质没有退步**：1000 域 MAE 差 −0.5%、控件数差 +1%，在单种子波动内（§2.18 的波动量级）。68 号已离线回读 diff 0（28,558 控件，maxDiff 0.46）；与 63 号同一条管线，没有单独上真机。

### 做了什么（按收益排序）

1. **光斑阶段（`spot-fit.mjs`）：2,045 s → 72 s。** 时间全在两处：候选表每放一个光斑就把所有相交项重算一遍，和精搜在 ±0.6R 窗口里逐点完整评估（开销 ∝ R⁴，所以画布从 500 加到 1000 时从分钟级涨到 34 分钟）。改成：① 一次评估最多抽 `--eval-cap 6000` 个 patch 像素；② 惰性候选表——放上光斑后只把相交项标脏，等它浮到堆顶才重算（小顶堆 + 版本号）；③ 精搜在窗口里抽样扫描、保留前 `--fine-topk 12` 个位置再完整评估；④ 每放 `--refresh 25` 个光斑把脏项统一刷新一遍，补回惰性贪心漏掉的「别的光斑放上去后收益反而变大」的候选。**1000 px 的光斑层 MAE 22.876（原 22.898），400 px 23.23（原 23.22）**。旧行为：`--no-lazy --exhaustive --eval-cap 0`。
2. **几何微调：只读评估 + 只处理覆盖率变了的像素。** 旧写法每试一个候选动作都要「删旧形状 → 插新形状 → 重算像素 → 不行再整个撤销」，而被拒的占绝大多数。现在试探不碰像素堆栈（`renderAlt`：假如这个形状在这个像素上的覆盖率换成 a，会渲染成什么），而且新旧覆盖率相同的像素增量恰好是 0，直接跳过——大光斑一次移动只动边缘一圈。**与旧写法逐项输出相同**（含 float32 舍入：评估结果也 `fround`）。带光斑种子的 400 px 上几何微调约 2.7×。
3. **覆盖率光栅化（`coverageInto`）：2.86×。** `Math.hypot` 比 `sqrt(a²+b²)` 慢得多，三角形的常量每个超采样点都在重算。改完后 6000 个随机形状（五种、含对称整数难例）**逐像素、覆盖率逐位相同**；`check.mjs --selftest` 里常驻一项对拍，参考实现冻结在 `coverage-ref.mjs`。这一项也是搜索线程的大头：400 px、同为 3 线程，三遍搜索的线程池耗时 376 s → 88 s（4.3×）。
4. **矩形边微调：只评估贴边的一行 / 一列。** 同样与旧写法输出逐项相同。
5. **分块并行精修（`shapes-tiles.mjs` + `shapes-refine.mjs`）：精修 316 s → 190 s。** 一个形状的评估 / 修改只碰自己覆盖的像素；包围盒完全落在某个分块里的形状，它的所有移动都被限制在分块里（`bounds`），所以不同分块里的形状互不影响，可以各自丢给一个工作线程。分块边长 ≈ 图边长 / 5（64～256），依次用四种错开半格的网格（`DSH_TILE_GRIDS=2` 退回两种），都装不进的（大光斑、大矩形、底板）由主线程**先**串行处理（它们在画序里多半靠下，串行时本来就先动），工作线程再精修上面的小形状。工作线程在共享内存里写 `cur` / `err`（分块互不重叠，不会互相踩），回传有变化的形状，主线程只改变了覆盖率的像素的堆栈。
   - **不是逐位等价**（动作顺序变了），所以单独验：`DSH_REFINE_CHECK=1` 每轮从堆栈重算全图核对共享内存，**1000 px 四轮都是 0 个像素不符**；`fitShapes` 收尾也常驻同样的自检（`stats.stackMismatch`，非 0 会在日志里警告）；自检里并行 vs 串行 MAE 差 ≤ 4%（实测并行 0.924 / 串行 0.932）。1000 px 带光斑种子的两轮精修：串行 33 s + 21 s → 四网格并行约 17 s + 10 s，MAE 4.115 vs 4.101、控件 14,972 vs 15,038。
   - 关掉：`--no-parallel-refine`（`shapes.mjs` 命令行）。图小到分块少于 4 个、或只有 1 个线程时自动走串行。

### 试过没用的（别重复）

- **光斑精搜「由粗到细」的分层搜索**（步长 R/6 起每级减半）：既没更快（候选表重算才是大头）、光斑层 MAE 还差 1.5%（23.56 vs 23.22），已删。
- **把形状搜索的线程从 8 加到 12 / 15**：400 px 单遍 11.9 s → 10.5 s → 10.3 s，几乎不再快，而且批大小 = 线程数 × 16，批越大快照越旧，控件数 / MAE 的取舍点会漂（12 线程：控件 −2.7%、MAE +1%）。默认仍是 8。
- **只收紧精修轮数**（第 4 轮约 23 s 换 0.6% MAE）：没动，这是画质 / 时间的取舍，不是白赚的。
- **GPU 联合梯度精修**（2026-10-21，PyTorch + CUDA，RTX 5060 Ti，原型 `gpu_refine.py` 在实验目录，没进技能）：把全部形状的几何 / 不透明度 / 颜色放进可微渲染（按 8×8 分块做画家算法合成），对 L1 误差一起做梯度下降，拓扑不变。**三种做法都没比现有 CPU 精修好**：
  1. 软覆盖率（`clamp(0.5 − sd)`）全参数：软模型下初始 MAE 1.75、精确模型下才 1.17——两个模型差太远，优化到软模型 0.93 后用精确模型评测反而是 **1.85（比 CPU 的 1.17 差 58%）**。
  2. 前向精确（4×4 超采样）+ 反向软梯度（直通）：几何一动就把结果打坏（两步后 1.17 → 2.15），因为精确覆盖率对几何是分段常数，软梯度只是个粗略的替身，所有形状同时挪一点点噪声就叠起来了。
  3. 只优化颜色 + 不透明度（覆盖率固定，前向 / 反向都精确）：30 步没有一步比起点（CPU 精修后的 1.1679）更好，最低就是起点，收敛后在 1.19～1.22 打转。说明 CPU 逐形状的最小二乘颜色重拟合已经接近联合最优。
  每次迭代 10～15 秒（启动开销为主），400 px 就要十几分钟，也不划算。**真正值得上 GPU 的是形状搜索**（占构建 60%）里的「候选打分 + 爬山」——那是纯提速、不改画质，已经做了，见下面「GPU 形状搜索」。

### GPU 形状搜索（`--gpu`，2026-10-21，实验性）

把 `searchSeed` 的「打分 + 爬山」整个搬到 GPU 上（`gpu_search_kernels.py` 是 Triton 内核，`gpu_search_server.py` 是由 `shapes.mjs` 起的子进程，`shapes-gpu.mjs` 是 Node 端客户端）。起点列表（`initFromRegion` + `initsFor`）仍由 JS 算，`tryAdd` 仍是 CPU 上的精确判据，所以 GPU 只影响「候选从哪来」，不影响结果的正确性。

| | CPU 线程池（8 线程） | GPU（RTX 5060 Ti） |
|---|---:|---:|
| 1000 px 完整构建（68 号 vs 90 号，同参） | 706 s | **448 s** |
| 其中形状搜索三遍 | 414 s | **约 56 s**（含首遍的内核加载） |
| 控件数 / 构建 MAE | 28,555 / 2.058 | 28,162 / 2.071（持平） |
| 400 px 单遍内核吞吐 | 约 110 万次评估 / 秒 | **586 万次评估 / 秒（≈ 5×）** |

- **对拍**：400 px、3000 个样本种子，GPU 与 CPU `searchSeed` 的候选**种类一致 99.8%、种类与参数完全一致 99.2%**，得分相对差中位数 6e-8（差异来自 float32 与 float64 在边界采样点上的舍入）。`check.mjs --selftest --gpu` 常驻一项（GPU 真的处理了种子、收尾自检 0 个像素不符、MAE / 控件数与 CPU 差 ≤ 4%）。
- **内核**：一个 GPU 程序跑一次完整的爬山（5 级步长的状态机，只有一个打分调用点）；候选的 4×4 超采样覆盖率与 `coverageInto` 同一套分类；**可删数**（候选能取代几个现有形状）用「每个持久程序一行私有计数数组 + 原子加」精确计数，不用预先枚举候选表（实测候选在爬山中会比起点包围盒长出 p50 = 10 px、p99 = 41 px，预先列表在密集区会有上千项）。提速三步：8×8 瓦片 + 2 个 warp（1.3×）、整块瓦片都不在边带里就跳过 16 次超采样、把第 1 遍算出的覆盖率缓存起来给后 3 遍用（2.2×）。
- **批大小要按图面积定**：同一批里的种子都在同一份旧快照上算，批越大越快、互相重叠的越多、质量越差。400 px：批 128 与 CPU 完全一致（控件 12,986 对 12,996、MAE 3.336 对 3.336），256 / 384 批 MAE +1% / +2%。重叠程度取决于「一批种子占图的面积比」，所以默认批 = 像素数 / 1250（400 px → 128，1000 px → 800），`--gpu-batch` 可改。
- **依赖与退路**：需要 PyTorch（CUDA 版）+ Triton（Windows 上是 `pip install triton-windows`；本机试过 triton-windows 3.8.0 + torch 2.11+cu128 + Python 3.14 + RTX 5060 Ti / Blackwell sm_120，能跑）。第一次要编译内核（约 1 分钟，之后有磁盘缓存）。起不来（没装 / 没 CUDA / 编译失败）就记一行警告并**自动退回 CPU 线程池**；`--no-rotation` 与软边 kind 5 暂不支持 GPU（也会退回 CPU）。
- **没改的东西**：`tryAdd`（精确评估并放上去）、精修、光斑。光斑（约 120 s）与精修（约 210 s）现在是 1000 px 构建里最长的两段。
- **同步的做法**：Node 端对 `cur / err / topArr / vis / alive / bb` 各留一份影子数组，每批前逐元素比对，只把变了的发给 GPU（400 px 每批约 5 ms），不需要改 `fitShapes` 里任何热路径。

### 现在的瓶颈

用 `--gpu` 后，1000 px 的构建里形状搜索只剩约 1 分钟；最长的是精修（约 210 s，其中主线程串行处理那 300～650 个大形状每轮 8～16 s）和光斑（约 120 s，单线程）。再想提速要么换光栅化的思路（只算边缘一圈），要么让大形状的候选动作也并行评估，要么把光斑的评估也搬到 GPU——都没做。

## 3. 参数

| 参数 | 含义 | 取值建议 |
|---|---|---|
| `--std` | 每个矩形内三通道标准差上限；0 = 只合并完全同色（无损） | 起手 3。【第三方】经验：MAE ≤ 1.5 一般看不出，≥ 3.5 明显 |

| 参数 | 默认 | 作用 |

行为：再次建立时复用已有控件（只改尺寸、颜色、位置，多余的 `SetActive(false)`）；**建立期间分组是隐藏的**，建完每帧放出一组；全部显示后 `script:EnableUpdate(false)`。下面两种情况会自动回退为「直接挂在宿主控件下、全程可见」——画面正常，只是建立期间与稳态的帧开销高约 9 倍，日志会报一句 `⚠️`：
1. 分组控件本身建不出来（模板/宿主不允许）；
2. **能在宿主下建控件、但建不出「挂在隐藏父级下的子控件」**。这条用一次性探针发现（隐藏分组之后新建一个控件再销毁，1 次实例化 ≈ 0.22 ms）——整条设计依赖「隐藏父级下也能建子控件」，而这个前提在本技能里只来自【第三方实测】。没有探针的话，这条路走不通时表现是「块全部建立失败、画面空白」。

### 模板与部署【第三方：原作 README，未经本技能核对】

1. 编辑器 → 界面控件组管理 → 界面布局 → 布局详情/自定义 → 选「客户端控件容器」→ 画布设置【前往编辑】→ 添加「图片控件」→【存为模板】。必须存为**客户端控件模板**，不是服务器元件。

   **路径本身已在真机证实可用**（2026-10-19 本机扫描 + 实际替换 `main.lua` 后 `lint`/`smoke` 均通过）；**国服/国际服的完整根目录、多 uid 判别、跨服重号陷阱见 `lua-ui-playbook.md` §探针怎么落盘**——两个服的根目录不同（`原神` / `Genshin Impact`），别只扫一个。

### 6.1 稳态帧开销、建立耗时模型与看门狗

【第三方实测：[wwh177/miliastra-image-algorithm](https://github.com/wwh177/miliastra-image-algorithm) 的 `render.lua` 头注释与 `2D项目-skill`（2026-10）】
**未在本技能真机复验。** 本技能已按这套结论改了自己的 `render.lua`（§5 的 `GROUP_HIDE` / `GROUPS`）；离线模拟只验证了「分组确实建立、块确实在隐藏的父级下建立、建完确实逐帧显示」，**性能收益本身仍是第三方的数字**。

| 项 | 数值 | 对本工具的含义 |
|---|---|---|
| 稳态每帧开销 | **可见控件数 × 15~18 µs**：5,000 → 12 fps；20,000 → 3 fps；40,000 ≈ 0.6~0.7 s/帧（1.5 fps 上下） | 这是块数上限的**真正原因**，不是存档大小。4 万控件的图能进、能看，但别指望它动起来 |
| 隐藏时的稳态开销 | 父级 `SetActive(false)` 时 **≈ 1.7 µs/个**，约 **1/9** | 建立期间把块挂在隐藏分组下，`FRAME_BUDGET` 分期才真的不卡 |
| 建立耗时模型 | **≈ 0.27·N + 3.75e-6·N² ms**（N = 块数）；20,000 块 ≈ 6.9 s | 与「0.223 ms/个」的线性估算差不太多，N 大时二次项才明显 |
| 单次回调上限 | 约 **20~22 s** 后被引擎截断：**不报错**，数据没建完、画面缺一块（早期文档写 20 s，新文档写 22 s） | 用 `FRAME_BUDGET > 0`（默认 12 ms/帧）就碰不到；设 `0` = 一次建完，大图必踩 |
| 变可见的开销 | 一帧内让全部控件变可见 = 一帧重建整批渲染 → 卡顿 | 所以「显示」也要分帧：`GROUPS = 16`，每帧放出一组 |
| 隐藏方法 | 必须**冒号调用**：`c:SetVisible(false)` ✓ ／ `c.visible = false` ✗（静默失败） | `render.lua` 的 `SetVisible` 与 `SetActive` 都调，并把 `pcall` 返回值记下来，失败时报一句 |

**本技能 2026-10-19 真机核了这张表里的两条（695 个可见控件，关卡 `1073872924`，详见 §6.1.2 / §6.1.3）：**

- **「变可见的开销＝一帧重建整批渲染 → 卡顿」在 695 个这一档不成立**。一帧内让 695 个全部由隐藏变可见，首帧 17.00 ms、3 帧均值 16.67 ms，相对基线 +0.47 / +0.14 ms，**没有可测的卡顿**。这条警告要么只在大得多的批量上成立，要么本来就偏保守。
- **「695 → 87 fps」这类外推不可观测**：引擎封顶 60 fps，695 可见与 0 可见**同帧时间**（都是 16.57 ms）。`15~18 µs` 既没被证实也没被推翻，仍是第三方数。

「隐藏 → 建立 → 分帧显示」已在 `render.lua` 实现（`GROUP_HIDE = true`，默认开）。分组是全屏透明控件、居中挂在宿主下，块控件的坐标不用改；分组创建失败时回退成老做法并报一句 `⚠️`（画面正常，只是慢）。
**`to-gil.mjs --hide active|visible`（填色期间隐藏批容器）是同一思路的另一半，仍未真机验证。**

#### 6.1.1 真机实测：改属性单价（2026-10-19，本技能自己的探针）

上面那张表里「改属性约 0.012 ms」是**唯一被真机直接推翻的数**。条件：关卡 `1073872924` / 695 控件 / 编辑器 7.1.0 / 日志 `日志_2026/10/19_01:19:04_玩家_ZYinBow`（v1）与 `日志_2026/10/19_01:29:12_玩家_ZYinBow`（v2）。

| 操作 | 真机实测（v1 / 单次） | 真机实测（v2 / 30 遍） | 上表/第三方 | 备注 |
|---|---:|---:|---:|---|
| `anchoredPositionX/Y` 写 | 1.68 µs | **1.92 µs** | — | v1 偏低 12.5% |
| `sizeDeltaX/Y` 写 | 2.40 µs | **2.04 µs** | — | v1 偏高 17.6% |

| 收集全部子控件（`GetChildren` 两层） | 1.44 µs/个 | — | — | — |

**v2 的 30 遍复测把 v1 的单次值修正了 ±18%**（v1 每项只有 10 个样本，±0.12 µs 量化叠上调度抖动，比理论误差大两倍）。**以 v2 那一列为准**：位置 1.92 / 尺寸 2.04 / 颜色 2.11，三者相差 <10%，说明这个量级由 **FFI / 封送**决定，不是属性本身——所以不要再按「哪个属性更便宜」做设计，按「少写几次」做。

能力探测 12 项全 OK：`GetAnchoredPosition` / `GetSizeDelta` / `anchoredPositionX` / `anchoredPositionY` / `sizeDeltaX` / `sizeDeltaY` / `SetAnchoredPosition` / `SetSizeDelta` / `SetVisible` / `SetActive` —— **「脚本能不能改控件几何」这个问题不用再怀疑了**。控件树两层（宿主 → 分组 → 块），首块 `位置=(0,0) 尺寸=(640,896)`。

**三条读法上的坑：**

1. **`os.clock()` 在真机只有 1 ms 分辨率。** 五个测量值全部落在整数毫秒（7.00 / 10.00 / 4.00 / 5.00 / 1.000），这是 Windows `clock()` 的 `CLOCKS_PER_SEC = 1000`。所以表中数的相对误差是 **5%～12.5%**（±0.5 ms 量化），**不要当三位有效数字用**。要更准就把循环加到总时长 ≥ 100 ms（探针 v2 已改成 30 遍）。
2. **这测的是 API 调用，不是渲染。** 探针在 `OnStart` 里跑，**一帧都没渲染**，量到的全是调用成本。上表最重的「可见控件 × 15~18 µs/帧」是**画布重建**开销，这次完全没碰到，**仍然只有第三方数**。
3. **完整填色路径比属性写单价贵得多，而且贵的部分不是 `SetImage`。** 两次运行：v1 `填色 695 块 = 0.02 s`（28.8 µs/块）、v2 `0.01 s`（14.4 µs/块）——同一条路径**跑两遍差一倍**，说明大头是**一次性解码**，不是每块写入。v2 实测 `SetImage 可用 = false`（这个方法不存在，填色走的是别的路径），所以旧猜测「每块多一次 `SetImage`」**被推翻**；剩下的候选只有 `IMG.DATA`/`IMG.SHP` 字符串解码。**结论：这部分可以在脚本外预解码掉，不要按「控件数 × 属性单价」估总时间。**
4. ~~**`SetImage` 不是控件方法。** v2 用 `pcall(c:SetImage(100001))` 直测，返回 `false`。要用图片请查 `api/client-ui-api.md` 的实际字段名，**别照抄第三方示例里的 `SetImage`**。~~ **❌ 这条是错的，2026-10-19 真机证伪**——见下面 4b。探针只传了 **1 个参数**，而正确签名是 **2 个**（来源枚举 + 图片 ID）：`c:SetImage(Enum.ImageSource.StaticReference, 100001)`。参数个数不对时 Lua 抛错、`pcall` 返回 `false`，与「方法不存在」在探针里**不可区分**——这是探针设计缺陷，不是引擎事实。

4b. **`SetImage(来源, ID)` 确实是控件方法，而且新式图片控件「不设图片就是整屏 `?`」。**【实测·真机 2026-10-19 22:56，关卡 `1073872927` / 1400 块 / 编辑器 7.1.0】

   - **症状**：视频关卡里 1400 个图块**全部**画成引擎的「?」占位符——按块尺寸拉伸、**颜色是对的**（`imageColor` 正常生效）、几何与运动也对。看起来像「字」，其实是缺图占位。
   - **对照**：`style-fit/立绘_695控件.gil`（同底关卡、同一套 `to-gil.mjs` 克隆出的图片控件、节点槽位逐项一致）显示正常，差别只有它每块都调了 `SetImage(Enum.ImageSource.StaticReference, 100001)`，而视频运行时为了省写入**没有调**。
   - **结论**：新式图片控件的图片源**不写进 `.gil`**（存档里没有该字段，与「颜色字段未知」是同一类问题），必须由脚本给。**没有 `SetImage` 的块不是「默认纯色」，而是「?」占位。**
   - **代价**：`OnStart` 里每块一次，1400 块约 3 ms（按 1.92 µs/次估），只需一次、循环回绕不用重设。
   - 【待真机】补上后的版本（`就绪 v2.1 … 贴图 1400`）已于 2026-10-19 22:59 部署，等我方确认。

| A9 可见性 全显示 | 17.00 | 16.67 | +0.47 / +0.14 |

**结论：695 个控件全改几何，帧末代价约 0.8～1.5 ms（均值）、最坏单帧 4.5 ms。** 不是 230 ms，不是 306 µs/控件——**v2 那个数高了 50～250 倍，「换镜头会卡 0.2 s」的判断作废。**

**v2 错在哪（通用教训）：** 它在量「帧末重建」之前先用大循环做了 8.3 万次写入，那些脏状态全部积压在同一帧，然后才做「几何全改」。**任何「先做大循环、再在同一帧量大改动」的探针都会把循环的账算到大改动头上。** 干净的测法必须让被测动作是那一帧唯一的写入。

**必须承认的局限：这份数据贴着噪声底。**

- 结论踩在 60 fps 帧率上限上（基线 16.53 ms = 60.5 fps），**任何低于一帧预算的开销都被上限吸收**
- `os.clock` 只有 1 ms 分辨率，单帧 ±1 ms，3 帧均值 ±0.58 ms
- 除 A1/A2 外，其余 7 个测点全部落在 ±0.5 ms 内 = **与基线不可区分**

**所以「一次性 / O(N) / 每次全量」仍然没分辨出来——但这个分支没有架构后果。** 三种假设在本关都指向同一个量级（≤4.5 ms），双缓冲换镜头不会卡。分支只在「N 涨到 1,400 时要不要错开第一帧」上有区别，那点差别在 43 fps 的预算里可以忽略。

**v3 自己的判定逻辑也写错了，一并记下：** 判定② 打印 `174/695 = 0.944`，那是把**绝对帧时间**相除（`17.00 / 18.00`）。正确要除**超出基线的量**：`0.47 / 1.47 = 0.32`（首帧）或 `0.47 / 0.80 = 0.59`（均值）——两个都在噪声里。判定① 的 `1.17`（`21.00/18.00`）同样只用两个单帧；判定③ 的「尺寸项贡献 6%」也是绝对时间相减。**绝对帧时间里有 16.5 ms 的引擎底噪，两个绝对时间相除等于把底噪也除进去，结果必然趋近 1、看起来「与改动无关」——那是假象。**

**只动父容器的对照（A7）**：+0.47 / +0.14 ms，同样贴基线。**在这个量级上，「逐块改几何」和「只动容器」都便宜，不需要为此改架构。**

#### 6.1.3 真机实测：每帧渲染开销 R —— **本技能自己的 v2 推错了，别引用那个数**

【实测·真机：同上日志。**这是本技能的一次方法错误，写下来避免复犯**】

v2 探针打印了 `R ≈ 1.17 µs/控件/帧（1233 fps 上限）`。**这个数不成立。** 原始三段：

| 阶段 | 可见数 | 均值帧 | 状态 |
|---|---:|---:|---|
| 1 | 695 | 17.38 ms（57.5 fps） | **自由运行**（唯一有信息的一段） |
| 2 | 348 | 16.56 ms（60.4 fps） | **撞帧率上限** |
| 3 | 0 | 16.57 ms（60.3 fps） | **撞帧率上限** |

**错在哪：** R2 用的两个端点（阶段 2、3）**都贴在上限平台上**，它们之间的 `-0.03 µs` 是噪声不是数据；探针却把 `R1`（唯一有效）和 `R2`（被截断）**做了算术平均**。用一个自由点加一个截断点平均，得到的是伪精确。

**能得出的只有区间：**

- `work(695) = 17.38 ms`（自由点）
- `work(348) ≤ 16.56 ms`，`work(0) ≥ 0`
- ⇒ **R ∈ [2.36, ~17.8] µs/控件/帧**（上界用 `work(0) ≥ 5 ms` 收紧）

**第三方的 16.5 µs 没有被排除，它正好卡在这个区间上沿。** 所以「每帧 16.5 µs × N」这个模型**既没被证实也没被推翻**——它仍然是第三方数，不能当实测引用。

**正确的测法：二分找交叉点。** 逐步减少可见数，找到「帧时间刚好贴住上限」的 `n*`；此时 `work(n*) = 上限平台`，于是
`R = (work(695) − 上限平台) / (695 − n*)`。
两个点都在自由运行区，才除得出斜率。**前提是至少有一个点超过上限。**

**v3 跑了这个二分，结论是「本关测不出」。** 0 可见 16.57 ms、695 可见 16.57 ms、中间 348/521/608/651/673/684/689 全部落在 16.53～16.60 —— **695 个可见控件整整齐齐地待在上限平台下方，没有交叉点可找。**

**这本身是个有用的结论**：若按第三方 16.5 µs 外推，695 × 16.5 = 11.5 ms，加上引擎底噪已接近 16.5 ms 的预算——实测却是 0 可见与 695 可见**同帧时间**，说明渲染单价大概率显著低于 16.5 µs。但要给出确数，**必须让可见数超过 695**（本关只有 695 个块，没有余量）。**要测 R，只能新建一批控件把可见数顶上去——而那会改变被测对象本身。** 实践上更划算的做法是直接做真实的双缓冲、看实际帧率，而不是再设计一轮探针。

**写这类探针的第 4 条硬约束：**

4. **截断数据不能参与平均。** 引擎有帧率上限时，「低于上限的一切」都读到同一个数——那是上限，不是被测对象的开销。**先判定每段是否触顶，只用触顶之上的数据算斜率；只有一段触顶就老老实实报区间，不要给点估计。**（v2 的 `mx-mn/mx < 2%` 判据也没用：三段差 4.7% 就绕过了它，而实际上有两段是截断的。）

#### 6.1.4 写这类探针的硬约束（合计 6 条）

1. **绝不忙等 `os.clock()`**。离线模拟器里 `os.clock` 是「当前虚拟时刻」（`scripts/lib/sim/world.mjs:88` 的 `clock: () => this.t`），**单帧执行期间不推进**——`while (os.clock() - t) < 0.05 do end` 在真机是 50 ms 忙等，在模拟器里是**死循环**（v2 初版就是这么把 `sim-lua.mjs smoke` 挂住 120 s 的）。阶段推进一律用 `OnUpdate` 的 `dt` 累加，再叠帧数硬上限兜底。
2. **模拟器没有性能模型**：帧率是固定 30 fps 虚拟时钟，所有属性写都报 `0.0 ms`（同一份脚本，真机填色 `0.02 s`、模拟器 `0.00 s`）。探针在模拟器里只能验「不崩、各阶段都跑到」，**任何 µs 数都只有真机能给**。
3. **fps 必须用斜率取，不能用单段帧时间**：单段里混着引擎基础开销，除不出每控件单价。但**斜率法要求至少两段都在上限之上**，否则退化成 §6.1.3 的错误。
4. **截断数据不能参与平均**（见上）。
5. **比值一律用「超出基线的量」，不用绝对帧时间。** 绝对帧时间里含 16.5 ms 级引擎底噪，两个绝对时间相除结果必然趋近 1，会把「O(N) 的重建」误判成「与改动无关的全量重建」——v3 的判定② 就是这么错的（`17.00/18.00 = 0.944`，正确是 `0.47/1.47 = 0.32`）。同理，**每个测点的基线必须当场重测**，不能沿用上一轮的数。
6. **被测动作必须是那一帧唯一的写入。** v2 在量帧末重建之前先跑了几万次写入，把循环的账全算到了那一次改动上（230 ms vs 真实 1 ms）。**先做沉降，再让被测动作独占一帧。**

> 探针源码在工作区 `style-fit/真机探针.lua`、`真机探针2.lua`、`探针3.lua`（不随技能分发）；部署与回滚见 §5 第 3 条，路径规则见 `lua-ui-playbook.md` §探针怎么落盘。

#### 6.1.5 镜头能不能只动容器？——**能**，1390 次写降到 2 次（真机已验，2026-10-19）

**动机。** §2.17 的双缓冲 / 换镜头模型里，每帧改写 `W` 个大头是 `4 × N × 2 µs`。如果整张图全在**同尺寸、同位置**的容器里，那么「缩放 + 平移」可以只作用在容器上，子控件跟着走——**每帧 2 次写（1 次 `SetLocalScale` + 1 次 `SetAnchoredPosition`），而不是 4N 次**。这不是优化，是量级差异。

**结构前提（本关 `1073872924`，离线 `sim-lua.mjs tree` 读出的布局，属【逆向推断】）：**

```text
容器节点 640×896 @(0,0)
  批1 … 批11   全部 640×896 @(0,0)      ← 11 个容器，尺寸位置完全相同
    块1 … 块695  子控件，坐标即画布坐标（中心 (0,0)，x∈[−320,320]，y∈[−448,448]）
```

`rect-merge` 的分批（`BATCH=64`）把块装进 11 个**全画布、居中**的容器，正好满足前提。`GetPivot()` 读出 `(0.5,0.5)`，缩放基准就是画布中心，不需要修正。

**变换推导（写进脚本的那个式子）：**

```text
某点原画布坐标 c  →  父级缩放 k 后画在 k·c  →  父级再平移 t 后落在 k·c + t
要求它落在 k·(c − P)（P 是要放到屏幕正中的那个点）  ⇒  t = −k·P
若枢轴不在中心，缩放基准偏移 off = (pivot − 0.5)·size，补一项：t = −k·P + off·(k − 1)
```

所以每次只需 `SetLocalScale(k,k,1)` + `SetAnchoredPosition(−k·Px, −k·Py)`。

**三种实现（同一段运动、同一画面，只差改谁）：**

| 模式 | 改谁 | 每帧写入 | 预期 |
|---|---|---:|---|
| `root` | 只有 `容器节点` | **2** | 最便宜 |
| `groups` | 11 个 `批N` | **22** | 次便宜 |
| `blocks` | 695 个块的位置 + 尺寸 | **1390** | 参照组，≈2.8 ms/帧（§6.1.1 实测单价外推） |

**真机结果（2026-10-19，695 控件）——前提成立，`root` 可用、`blocks` 作废：**

| 模式 | 改谁 | 帧数 | 脚本合计 | **每帧脚本** | 均值 dt | fps |
|---|---|---:|---:|---:|---:|---:|
| `root` | 1 个容器 | 176 | 51.0 ms | **289.8 µs** | 17.10 ms | 58.5 |
| `groups` | 11 个容器 | 182 | 74.0 ms | **406.6 µs** | 16.57 ms | 60.4 |
| `blocks` | 695 个块 | 145 | 1158.0 ms | **7986.2 µs** | 20.77 ms | **48.1** |

**三点呈完美线性**：`每帧脚本成本 ≈ 280 µs + 11.1 µs × 控件数`（三点残差 ≤2%：`root` 预测 291 / 实测 290，`groups` 402 / 407，`blocks` 7993 / 7986）。

1. **`SetLocalScale` 存在且生效**（自检 `SetLocalScale=OK`，无报错）→ 原风险 1 排除。
2. **`blocks` 撑不住**：7.99 ms/帧 = 60 fps 预算的 48%，实测掉到 **48.1 fps**。§6.1.1 用「2 µs/次写 × 2780 次 = 5.6 ms」估算偏低——真实每块每帧 **11.1 µs**，因为一帧里是 4 次读 + 2 次写 + 2 次 `pcall`，不是 2 次写。
3. **`root` 的每帧成本与块数无关**：它只碰 1 个容器。N 从 695 涨到 1400、5000，脚本侧仍是约 290 µs。**这是动态内容整条路线成立的关键，也是本节最值钱的一条。**
4. **换镜头不掉帧**：演示阶段 4 次镜头切换，切换帧 dt = 17.00 / 16.00 / 17.00 ms，基线 16.53 ms，**无可测尖峰**。

**未归因的一项**：固定项约 280 µs/帧与「改谁」无关（三点拟合的外推值），可能是每帧的 `pcall` 闭包、`os.clock`、`string.format` 与 HUD `print` 的摊薄。生产版去掉 HUD 会更低；即使按 280 µs 算也只占 60 fps 帧预算的 **1.7%**，不改变结论。

5. **画面确实跟着变了**（真机目视，2026-10-19）：缩放生效，**且画面在不同位置之间移动了**。`root` 路线定案，不需要退到 `groups`。

**机位范围规则（做运镜必须知道，不写会露白边）。** 放大 `k` 倍后只看得见图面的 `1/k`，所以焦心必须落在中间那一块：

```text
0.5/k  ≤  fx, fy  ≤  1 − 0.5/k        （fx,fy 是 0..1 的图面比例）
k=1.00 → 只有 0.5 一个点（全景不能摇）
k=1.50 → [0.333, 0.667]
k=1.80 → [0.278, 0.722]
```

等价写法：`|px| ≤ 图半宽 − 图半宽/k`。超出这个范围，引擎会在边缘露出画布外的空白（背景是游戏世界，很难看）。生产版因此加了 `clampFocus`：焦心自动夹进范围（宁可构图偏一点，也不露白边），并在启动时把越界的段号打出来。

**脚本**：生产版 `（作者本机路径，未随技能分发）` 拼在原填色脚本尾部（`OnStart` → `do_fill()` 后接 `cam_init`），部署版见本关 `main.lua`。离线 `check-lua-ui` + `sim-lua lint` 均 0 问题、`smoke --gil 45 s` 0 错误、1350 帧跨 2.57 轮循环正常、启动自检无越界告警。

**生产版的可调项**（都在文件顶部 `CAM` 与 `SHOTS`）：

| 项 | 默认 | 说明 |
|---|---|---|
| `loop` / `maxLoops` | `true` / `0` | 无限循环；`maxLoops=N` 播 N 遍停 |
| `clampFocus` | `true` | 焦心夹进「不露白边」范围 |
| `clampDt` | `0.10` | 单帧 dt 上限，卡顿后镜头不会瞬移 |
| `resetAtEnd` | `true` | 停止时还原存档几何 |
| `SHOTS` | 5 段 / 17.5 s | `{时长, 起机位, 止机位, 缓动}`；**起止不连续即硬切**，连续即摇移 |

**缩放上限是画质问题、不是性能问题。** 成本恒为约 290 µs/帧，但每块放得越大块的边越快露出来；695 块这档建议 `k ≤ 1.6~1.8`，再往上画面会糊成色块。

- 想量「隐藏 vs 全程可见」的差别：把 `render.lua` 的 `GROUP_HIDE` 改成 `false`，`check.mjs render … --measure` 对拍引擎调用次数与帧数（实测 31,871 块的 300×300 图：可见 286,843 次调用 / 498 帧；隐藏 287,083 次 / 514 帧，多出的 240 次调用与 16 帧就是分组本身的开销）。**这测的是调用次数，不是帧率**——帧率收益要真机。
- `--edge-aware` 的回归门：⓪ 三条旋钮各有断言——`I` 最低 = 1−slack、最高 = cap（不是 1+boost）；`cap / slack` 的方向改用**同一份预算下的边带 / 其余 MAE**判（块数已被对齐锁死，旧的"块数更多/更少"断言在新语义下必然失效）；① `--edge-boost 0 --smooth-slack 0` 必须与不加权**逐字节相同**；② **预算对齐**：默认参数块数与基线差 ≤5%；③ 默认参数下**边缘带 MAE 降 ≥ 10%、其余升**；④ `--edge-unbalanced` 必须还能复现旧行为（块数明显少于基线）；⑤ `budgetMultiplier` 单测：权重全 1 → m=1，真权重 → `tile(T×m, weights).n` 回到 `tile(T, null).n`。边缘掩码由 `check.mjs` 自己用 Sobel 独立算，不复用被测算术。
- 加权接通到分层 / 形状之后，同一套门**按路径各走一遍**：`--layered` 与 `--shapes` 都要有「权重全 1 = 与不加权逐字节相同」与「边缘带 MAE 降 / 其余升」。形状那条要**固定线程数**再比（搜索是并行的，线程数不同结果不可比）；形状的 MAE 用 `renderItems` 渲染后按掩码拆，和 Python 侧 `mae_split` 同一口径。
- `--focus` 的门：① `--focus-gain 0` 与不加权逐字节相同；② 焦点区 MAE 必须降 ≥ 20%；③ 其余区域 |Δ| < 3%（预算不能从别处漏出去）。焦点 JSON 的四种坏输入（多余键 / 缺字段 / 空区域 / 越界）都必须报错且消息里点明是哪一项。
- 加权精修的门：`--shapes --edge-aware` 精修后的 MAE 不得高于 `--shape-no-refine` 的 1.05 倍。**这条抓到过一个真 bug**：`colorSweep` 把重要度并进 `w`，于是分子乘一次 `I`、分母乘了两次（`w²`），解出来的颜色整体偏 `1/I` —— MAE 从 3.3 掉到 28，而**控件数看着完全正常**。恒等测试（`I≡1`）和"边缘 MAE 下降"都抓不到它，只有"精修不许变差"能抓到。
- `render.lua` 的 `BUILD_MODE = "auto"` 两条分支也在自检里：小图必须一次建完（0 帧），把 `SINGLE_SAFE_MS` 压到 0 必须改走分帧（> 1 帧）。
- 容量 / 路线判定跑 `node scripts/rect-merge/plan.mjs --selftest`（19 项：常数、单调性、存档边界 42281/42282、看门狗、崩溃阈值）。

- **`check-lua-ui.mjs` 不能代替 `sim-lua.mjs lint`：前者根本不查语法。** 2026-10-19 实测：一个只有 `local t = { in = 1 }` 的文件（`in` 是 Lua 保留字，真机加载必失败），`check-lua-ui` 报「未发现问题」，`sim-lua.mjs lint` 报 `LS001 语法错误：unexpected symbol near 'in'`。所以交付前**两个都要跑**，而且以 `sim-lua lint`/`smoke` 为语法门。这次就是靠它抓到一个 `EASE.in` 的写法错误（正确写法 `["in"] = …`）。
- 交付说明写明：源图与参数、块数（= 控件数）、MAE、编码、数据体积、模板与部署步骤、离线检查结果，以及「未在真机验证」。

## 8. 评估过、还没做的方向（按预期收益排序）

1. **把分层重长用在像素画精灵上**（例如死亡细胞复刻的图集）：无损就能少 36%～42% 图元。注意同一精灵内要保持绘制顺序，逐帧绘制的项目里每帧图元数同比下降。
2. **静态图片，运行时不再 Instantiate**：已有两条做法——§2.6 素材组 .gia、§2.7 编进关卡 .gil（几何静态、颜色 Lua 填）。新建控件约 0.223 ms、改属性约 0.012 ms【第三方实测】，3 万控件的建立时间基本都花在新建上。已做成 §2.6 的素材组 .gia 导出，等真机试验确定上限与表现。直接写进 `.gil` 控件树的路线：`.gil` 布局字段编号与素材组一致，颜色很可能也在图片组件 `#31 #4`，但未核实（方法：编辑器里只改一张图片的颜色、导出两份存档、`gi.mjs diff`）。

## 9. 试过但没有用的（别重复）

- **椭圆替换后处理**（2026-10-16 离线，`100002` 纯色椭圆）：在分层矩形结果上，从大矩形出发长出内切椭圆（椭圆内标准差 ≤ STD），把完全落在里面的矩形删掉。结果：500×500 插画 STD=4 少 1.3%（44,427 → 43,861）但 MAE 1.806 → 1.872；同 MAE 下纯矩形把 STD 提到 4.2 就有 42,939 块、MAE 1.883，**椭圆版反而多约 2%**。STD=8 少 3.2%、MAE +5.9%。死亡细胞背景像素画 STD=0 / 2 少 0.1% / 1.1%。最有利的合成图（抗锯齿的圆、椭圆、矩形叠放）STD=2 / 4 / 8 少 7% / 9% / 14%，MAE 同时 +13% ~ +17%。原因：形状边缘的抗锯齿像素、渐变轮廓才是块数大头，纯色椭圆省不到；椭圆盖住部分矩形后那些矩形的露出像素变了，还会让部分矩形标准差超标（实验里最差到 14～46，没做重新着色）。**这是按二值遮罩（边缘不混合）算的，当时的结论是不值得。**随后 18 号形状试验在真机确认了旋转 / 椭圆边缘有抗锯齿，改成按覆盖率混合、按率失真取舍，同 MAE 能少约 23%（见 §2.8），所以主流程用 §2.8 的做法，这条只作为「别再试二值遮罩」的记录。

- 换铺满式划分策略（全局最大面积优先、合并后处理、从逐像素按误差增量合并）：同 MAE 下只少 1%～6% 块（本机离线，2026-10-15）。允许重叠的 §2.5 才是有效方向。

- **按"细节区 / 平坦区"整片分配容差（上游的动态 STD）**：2026-10-17 离线上复跑上游算法，300×300、STD=3 时全图 MAE 从 1.07 劣化到 2.53——平坦区（约 59% 面积）被放了三倍容差，误差在那里累积成色带。同为"边缘优先"的目标，应该按**逐像素重要度**加权并把验收口径拆成边缘带 / 其余区域（§2.9），而不是整片换容差。

### 2.17.6 块数上探到 4000：两个会静默产出坏关卡的 bug（2026-10-20）

**结论：块数是画质的主杠杆，但它同时把两个「按 1400 块写死」的假设踩爆，且两者都不会报错——一个少建控件，一个读出垃圾索引。任何把 N 往上调的改动都必须先过这两关。**

#### 实测：N=4000 的收益（K=110，S=16，TH=4，18bit，逐帧解码对拍）

| N | K | TH | 脚本 | MAE | p90 |
|---:|---:|---:|---:|---:|---:|
| 1400 | 158 | 12 | 1.13 MB | 4.704 | 5.84 |
| 1400 | 158 | 4 | 1.73 MB | 4.265 | 5.20 |
| 2800 | 110 | 12 | 1.97 MB | 3.769 | 4.69 |
| **4000** | **110** | **4** | **4.31 MB** | **2.871** | **3.52** |

**几何地板**（每帧全量精确块均值）：N=1400 → 3.867；N=2000 → 3.363（K=110）/ 3.276（K=158）；N=2800 → 2.851；**N=4000 → ≈2.5（由 TH4 的 2.871 反推）**。地板 ∝ N^-0.5 左右，但**收益递减很快**。

**条目数对 N 是次线性的（低 N 段）**：N=1400 时 TH4 条目 1,228,717，N=4000 只有 1,689,996（1.37×，不是 2.86×）。所以从 1400 到 4000 体积不会随 N 等比例上涨。

> ⚠️ **这段的「到 8 MB 需要 N≈12000」外推已被 §2.17.7 实测推翻。** N≥4000 之后条目数**回到近似线性**：6000→2,535,607、7500→3,164,514（4000→7500 的 N 涨 1.875×，条目涨 1.87×），脚本 4.51→6.68→8.28 MB。**N=7500 就摸到 8 MB，拟合 713 秒**，不是小时级。教训：非线性只在低 N 段成立，**别用 1400→4000 的斜率外推**。

N=4000 的构成（字符）：几何 477,429（26,042 bit/段，是 3N−2 的 2.17 倍——`enc_bsp` 实际用的位比下界多）、段表 330、颜色表 57,831（19,277 色）、码长表 4,000、颜色流 3,487,629、索引流 470,957；合计 4,498,176 字符 → Lua 4,506,217 B。

#### Bug 1：`mk_rects.py` 用 `[[...]]` 包数据，编码里出现 `]]` → 长字符串提前闭合

- **症状**：N=4000 时 `to-gil.mjs` 报「**1139 个图片控件**」，而不是 4000。不报错、不回退、容器校验照样「通过」（它校验的是自己建出来的那 1139 个）。
- **原因**：`mk_rects.py` 的字母表是 `chr(48+v)`，v∈0..63，**包含 `]`（93 = 48+45）**；连续两个 v=45 就拼出 `]]`。N 越大越容易撞上。
- **修法**：按数据里最长闭合序列抬高 `=` 等级（`[=[`…`]=]`），`blocks.mjs` 的解析器本来就认 `/\[(=*)\[([\s\S]*?)\]\1\]/`。
- **反例（会漏掉这条的检查）**：「容器校验通过 + 控件树 0 提示」**不能**证明块数对——必须**显式核对图片控件数 == N**。

#### Bug 2：帧头条目数字宽写死 11 位，N>2047 溢出

- **症状**：`verify3.py` 抛 `IndexError: index 4071 is out of bounds for axis 0 with size 4000`。
- **原因**：`build_v3.py` 里 `CNTBITS = 11` 硬编码（上限 2047），而帧头条目数 `cnt` 可以等于 N。N=4000 时 `push(4000, 11)` **静默截断**，解码器读到的是垃圾索引。
- **修法**：`CNTBITS = max(11, int(N).bit_length())`；N=4000→12 位、N=6000→13 位。`CNTBITS` 已经写进 blob 传给 Lua，所以 Lua 侧不用改。
- **教训**：**只在 N=1400/2800 上调参时，这个位宽永远是够的**——它是一颗只在放大块数时才引爆的地雷。任何「按块数」定宽度的字段（条目数、块索引、码长表）都要用 `bit_length(N)` 而不是常数。

### 2.17.8 真机：体积不是顶，**每帧写入次数**才是；追帧逻辑会留下色块（2026-10-20）

【实测·真机 2026-10-20，关卡 `1073872931`（`video_7500.gil` 副本），日志用 `scripts/device-log.mjs` 读出；探针与说明在 `（作者本机路径，未随技能分发）`、`（作者本机路径，未随技能分发）`，不随技能分发】

**三条结论改写了 §2.17.1 的约束排序：**

1. **脚本体积不是 8 MB 以内的顶。** 8,281,125 B 的 v10（6 个长字符串）加载、运行正常，`首帧 153 ms`。§2.17.1「第一约束是脚本字节」在 8 MB 以内不成立。
2. **可见控件数不是顶。** 帧率探针：0 → 7,500 个可见**静态**控件，每档都是 16.57 ms（60 fps 封顶，超出基线 ≤ 0.01 ms）。第三方「16.5 µs/可见控件/帧」在静态画面下不成立（若成立应 +124 ms），§2.17 成本模型里那一项要删掉；隐藏控件 1.7 µs 那项同理没有证据。
3. **顶在每帧写入次数。** 改色脚本侧约 **2.7 µs/次**（含 Lua 循环与颜色计算；纯赋值 §6.1.1 是 2.1），引擎侧另约 **1.4 µs/次**（推断为画布重建）：

   | 每帧改色 | 脚本 | 帧间隔均值 / p95 | fps |
   |---:|---:|---:|---:|
   | 300 | 1.04 ms | 16.57 / 17 ms | 60 |
   | 1,500 | 4.08 ms | 16.56 / 17 ms | 60 |
   | 3,000 | 8.16 ms | 17.49 / 21 ms | 57 |
   | 7,500 | 20.21 ms | 30.42 / 38 ms | 33 |

   要保 60 fps，每帧写入约 ≤ 2,500 次；按视频 34.74 fps 的实时预算（28.8 ms/视频帧），每视频帧约 ≤ 7,000 次。**几何写也算写**：换段一次是 4 × N 次。

**v10 实播（N = 7,500 / K = 110）**：多数 2 s 窗口 20～59 fps，但视频第 150～370 帧一段**每轮都掉到 2 fps**（脚本 300～490 ms/帧），用户目视「**切镜头时变成大量色块**」。账算得出来：全片颜色条目 3.16 M + 几何写 110 × 4 × 7,500 = 3.3 M，合计约 6.5 M 次写 / 28 s，按 2.7 + 1.4 µs 约 26 s——**几乎吃满整段时长**，镜头密的地方必然掉帧。

**色块的成因【推断：代码 + 现象吻合，未离线复现】——`mk_lua3.py` 运行时的追帧逻辑：**

- 卡顿后一次 `OnUpdate` 补若干视频帧：中间帧 `applyFrame(true)` **只更新 `CUR`、不写控件**，最后一帧只写**该帧自己的条目**。跳过帧里改过颜色的块**直到下次再变化之前都不会被写**——这就是色块。§2.17.1「追帧要分写和不写」那条只对了一半：**不写可以，但要记脏块**。
- `applyGeometry()` 在跳过帧里照常把 7,500 × 4 个几何属性全写一遍，中间段的几何根本不会被看到。
- 两者叠加是正反馈：越卡 → 一次要追的帧越多 → 几何写越多 → 越卡。1,400 块在 60 fps 下几乎不追帧，所以 v3/v4 没暴露；离线 `sim-lua` 只有固定 30 fps 时钟、`verify3.py` 逐帧全解码，**两者都测不出这类 bug**。

**修法（2026-10-20 已实现在 `（作者本机路径，未随技能分发）`，离线验证通过；✓ 真机：v11 用户回报无色块，fps 最低 26、中位 50，见台账）**：

1. **循环里只解码，循环外统一写**：追帧循环只调 `decodeGeometry()` / `decodeFrame()`（更新 `GX..GH` 与 `CUR`，把改过的块记进脏集合）；每次 `OnUpdate` 结束时 `flush()` 一次——先写当前段几何（换过段才写），再把脏块每块写一次。被追过去的帧与段**从不落到控件上**。顺带修掉第三个问题：旧逻辑在一次要追满 40 帧时**整次更新一个控件都不写**。
2. **N 可以小于关卡块数**：多出来的块（整批 + 最后一批的尾巴）开局 `SetVisible(false)`，横幅打印「藏起多余 X 块」。同一个 7,500 块关卡能跑任意 N ≤ 7,500 的脚本。
3. **离线自检**（`mk_lua3.py … tele check`，只给模拟器用）：每次更新后读回全部块的 `imageColor` 与几何，和 `CUR` / 当前段几何比对。`sim-lua smoke --dt 0.25`（每次追 9 帧）与 `--dt 1.5`（每次要追 52 帧、被 40 帧上限截断）均 0 不一致；**变异测试**（每次只写最后一个脏块，模拟旧 bug）第一次更新就报 1,399 块不一致——证明这个自检抓得住这类错误。`sim-lua` 的固定时钟本身不会暴露追帧 bug，**必须加 `--dt` 把帧率压低**。
4. **规划按每视频帧写入次数**：换段那一帧 = 4N 几何 + 最多 N 个颜色 = **5N 次**，与 K、TH 无关；段内普通帧在 N = 4,000 时也只有约 3,900 次。所以严格按「每视频帧 ≤ 约 7,000 次」，**N 上限就是 1,400**。N = 7,500 的换段帧是 37,500 次（约 5 倍、按 4.1 µs 约 150 ms 一次），不是「超一倍」（旧说法按全片平均算错了口径）。

   | N / K / 判定 | MAE（离线） | 换段帧写入 | 超 7,000 的视频帧 | 全片写入耗时 / 28 s |
   |---|---:|---:|---:|---:|
   | 1,400 / 158 / TH 4 | 4.265 | 7,000 | 0 | 6.1 s |
   | 2,000 / 158 / TH 4 | 3.706 | 10,000 | 158 | 8.7 s |
   | 2,800 / 110 / TH 4 | 3.314 | 14,000 | 110 | 9.9 s |
   | 4,000 / 110 / TH 4 | 2.871 | 20,000 | 110 | 14.1 s |

   想在换段帧不超预算的前提下加 N，得把几何写摊开（例如双缓冲：下一段几何提前分几帧写进隐藏的第二套块）——那需要 2N 个控件，未做。

### 2.17.9 降帧率换画质：用户观感跟「每张画面」走，不跟源时间轴 MAE 走（2026-10-20）

每视频帧的写入预算跟着帧间隔走：每 d 个源帧显示 1 帧，预算 ≈ 7,000 × d，换段帧 5N ≤ 7,000 d ⇒ **N 上限 ≈ 1,400 d**。被跳过的源帧里开始又结束的短镜头整段不进脚本（d = 2 丢 2 段、d = 3 丢 9 段）。实现：`build_v3.py --step d`（几何复用全帧拟合缓存，段按抽中的帧重映射；`step = 1` 与改前逐字节相同），Lua 运行时不用改（`FPS` 与 `NF` 随数据走）。

两种画质口径给出相反的名次（离线，320×448，TH = 4，都满足各自预算）：

| 播放 | N / K | 每张显示画面 MAE | 源时间轴 MAE（34.74 fps，含运动损失） | 真机 |
|---|---|---:|---:|---|
| 34.7 fps（d = 1） | 1,400 / 158 | 4.27 | **4.27** | ✓ v11 |
| 17.4 fps（d = 2） | 2,800 / 110 | **3.31** | 4.90 | ✓ v12，**用户：观感更好** |
| 11.6 fps（d = 3） | 4,000 / 110 | **2.86** | 5.64 | v13 待测 |
| 6.9 fps（d = 5） | 6,000 / 110 | 约 2.4 | 7.49 | — |

**结论**：这类「看画」的视频，用户更在意每张画面的细节而不是动作连贯，**源时间轴 MAE 会误导**——它把「这一帧挂得久、动作跟不上」也算成误差。选档按「每张显示画面 MAE + 真机目视」，帧率下限由目视决定。工具：`（作者本机路径，未随技能分发）`（两种口径并排，只做统计）。

**试过没用：几何双缓冲 + 短镜头沿用几何（2026-10-20 离线，`（作者本机路径，未随技能分发）`）。** 设想是两套块、下一段几何在隐藏那套里提前分帧写好，切换帧只写 N 个颜色，峰值从 5N 降到约 N + 4N/L；只有 1～2 个显示帧的短段不换几何、沿用当前几何只改颜色。按「每显示帧写入 ≤ 7,000·d、一帧都不超」挑最佳（每张画面 MAE）：

| 播放 | 现方案（单套）最佳 | 双缓冲 + 沿用 最佳 |
|---|---|---|
| 34.7 fps | N 1,400：4.27（K 158） | N 2,800、沿用 L<3：3.56（−16%） |
| 17.4 fps | **N 2,800：3.31** | N 4,000、沿用 L<2：3.44（更差） |
| 11.6 fps | **N 4,000：2.86** | N 6,000、沿用 L<2：4.27（差得多） |

两个原因：① **降帧后短段占多数**（step 3 时 101 段里 71 段只有 1 个显示帧），这些段前后没有时间提前写几何，纯双缓冲的峰值仍是约 5N（20,126 对 20,000），控件白翻倍；② **沿用几何在切镜头后对不上内容**——旧几何套新画面比「块少但几何对」差得多（N 6,000 / 11.6 fps：2.42 → 4.27）。只有 34.7 fps（短段少）有收益，但那时 17.4 fps 单套已经更好。**结论：降帧率下单套就在前沿上，别再走这条路**；要继续涨画质看拟合分辨率（§2.18 的画布密度思路，需原始视频）与 24 bit 色。

**拟合分辨率（2026-10-20 离线；`fit_hires.py` 并行拟合 + `eval_screen.py` 屏幕口径）：视频上只有 −4.5%，远小于静态图的 −18%～−32%。** 原视频 720×1008 用 INTER_AREA 缩到 320×448 与旧帧**逐像素相同**（确认同源同法），再缩出 480×672 / 640×896 两档；同 N 4,000 / K 110 / step 3，统一在 640×896 上用面积模型（1920×2688 超采样最近邻 → 3×3 平均）对原片 INTER_AREA 640×896 量每张画面 MAE：

**24 bit 颜色（2026-10-20 离线；推翻 §2.17.4「24 bit 不划算」——那是 1.23 MB 脚本预算下的结论，8.28 MB 已真机能加载后不再成立）。** `build_v3.py --cbits 24`：颜色 = 块均值原值，调色板每色 4 字符，颜色码格式不变（rank 码，上限 2¹⁸ = 262,144 种，超了构建直接报错）；`mk_lua3.py` / `verify3.py` 按 parts 里的 `CBITS` 解码，18 bit 时输出与改前逐字节相同。同 480 拟合 / N 4,000 / step 3 / TH 4：
